## 一、先纠一处名：是 SCOR，不是 SOCR

指令原文写的是「SOCR 体系」。**检索零命中名为 SOCR 的供应链体系；五条结果全部指向 SCOR**（Supply Chain Operations Reference，供应链运作参考模型）。

**判断：SOCR 系 SCOR 之笔误。**（推论。依据＝SOCR 检索零命中 + 全部结果收敛于 SCOR。）

**归属沿革（事实）**：1996 年由管理咨询公司 PRTM 开发，同年 Supply-Chain Council（SCC）成立；SCOR 由 SCC 发布；2014 年并入 APICS；现由 **ASCM**（Association for Supply Chain Management）维护，属**开放获取**标准（Creative Commons）。

**两版命名必须分清——这是本库第一处「同物异名」，两条路径都要能检索到：**

| | 传统版（v11 / v12，流传最广） | 现行 **SCOR DS**（ASCM 官网现行标准） |
|---|---|---|
| 流程数 | **6** | **7** |
| 名单 | Plan · Source · Make · Deliver · Return · **Enable** | **Orchestrate** · Plan · **Order** · Source · **Transform** · **Fulfill** · Return |
| 变化 | Enable 为后期新增（第六个） | Make → **Transform**；Deliver → **Fulfill**；新增 **Order**；Enable → **Orchestrate** |

**本库采 SCOR DS 七流程为顶层骨架。**（判断。理由两条：① 它是 ASCM 现行标准，传统版属旧版；② 传统版把"客户下单"混在 Deliver 里，SCOR DS 单提 Order，对电商全链路的分辨率更高。）

**传统版六个名单一律作为别名进检索表**——同一个流程两套名字，都得查得到。

**SCOR 的另外两条结构（备用）：**

- **四层级**：Level 1 流程类型（Scope）→ Level 2 流程类别（Configuration）→ Level 3 流程要素（Process Elements）→ Level 4 实施活动（**不在标准范围内**）。
- **五绩效属性**：可靠性 Reliability · 响应性 Responsiveness · 敏捷性 Agility · 成本 Costs · 资产管理效率 Asset Management Efficiency（SCOR 框定 **250+ 指标**，均挂这五条）。

## 二、分类骨架：主干 8 组 + 基础 3 组

**一个必须先认的判断：SCOR 是流程模型，不是概念模型。**

它能挂住"作业与流程类"名词，**挂不住主数据、空间容量、计量、单据**——`库容` 不属于任何单一流程，`SKU` 也不属于。若强塞进 Orchestrate（其下有 data & technology 一项），会把"主数据"与"使能"混成一团，反而更乱。

故本库分两层，**并显式声明哪层是 SCOR、哪层是本库自设**（不得混为一谈）：

| 层 | 组 | 归属声明 |
|---|---|---|
| **主干** | A 治理与使能 · B 计划 · C 订单 · D 采购 · E 转换 · F 履约·仓储 · G 履约·物流 · H 逆向 | **SCOR DS 七流程**。其中 Fulfill 因电商侧"仓储"与"物流"体量悬殊，按 SCOR 的 **Level 2（配置层）**思路拆为两个浏览子组 |
| **基础** | I 主体与标识 · J 空间与容量 · K 单据与状态 | **本库自设，非 SCOR 内容** |

**归属规则三条（缺一条就会打架）：**

1. **一词只有一个主归属组**，其余组以链接进入。
2. **决策归计划，作业结果归履约。** 安全库存 / 再订货点 / ABC 分类是**决策** → 归 B 计划；可用库存 / 冻结库存 / 库存账是**作业结果** → 归 F 履约·仓储。
3. **横跨多流程的归基础层。** 单据（入库单 / 出库单 / 移库单）横跨 D/E/F/H → 归 K；标识（SKU / 批次 / SN）横跨全链 → 归 I。

**第 4、5、6、7 项是普通词典没有的——本库存在的理由就在这四项。**

### 5.2 检索三入口 + 一条反向

1. **按组浏览** — 十一组侧栏
2. **别名与拼音检索** — 命中别名须高亮，并提示"你查的是 X 的别名"（**传统版 SCOR 的六个流程名必须能查到现行 DS 版**，这是本库的第一条硬要求）
3. **标签过滤** — `△ 歧义词` / `★ 已有词条` / `◆ 已被覆盖` / `待拍板`
4. **反向索引** — 「**外部说法 → 本项目口径**」。痛点方向是"别人这么说、我方该怎么理解"，所以反查表比正查表更常用

### 5.3 静态站的硬约束

无后端 → **不能靠中文分词**。必须**预生成一份索引 JSON**（词条名 + 全部别名 + 拼音 + 组 + 标签 + 首字），前端做前缀与倒排匹配。**这是"静态"二字的代价，须提前认。**

## 反方审查

**反方 1｜这份词表在"你要的是一个能对外发布的名词站"时直接崩，因为我把定义剥离成了指针，对外发布就是一堆断链。**
**回应：部分成立，但这是刻意的。** 剥离定义是为了不造第三处真相源（§零 第 3 条）。**若目的是对外发布，必须换体例**——那时它不再是内部索引，而是内容资产，允许自写定义并承担维护成本。**这一条我反驳不了**，列为未决项 1。

**反方 2｜143 个词里，我真正核过来源的只有库容与 SKU 两个，其余 141 个是凭 SCOR 框架与领域印象铺的，来源未标。**
**回应：成立，接受。** 词表阶段只给"词 + 归类"，不给定义与来源；**但"归类"本身也是判断，也可能错**。**处理办法**：全部 `△` 词优先核来源，核完再升级为正式词条。**词表在核完之前只是待办清单，不是成果。**

**反方 3｜"基础 3 组自设"这一步，等于承认 SCOR 装不下这个概念体系，那"参考 SCOR"就只剩个名义骨架。**
**回应：部分成立。** SCOR 挂得住主干 8 组（107 词），挂不住基础 3 组（36 词）。**但我认为这不是挂羊头**——SCOR 的价值恰恰在提供 A–H 的**标准命名与流程边界**，这部分它做得比任何中文术语表都好；而基础层本就是 SCOR 声明范围外的（它的 Level 1 是流程，不是数据）。**这条我保留判断：骨架是 SCOR 的，边界是自设的，两者都已标注。**

**反方 4｜把「SKU」标成 `★◆` 双标，又在词表里占一行，会让读者以为本库有它的定义。**
**回应：接受，已改。** `02-` 文件名与本节 §四 都写明"**不重写定义、只做对照补页**"，且词条首行即回指既有文档。**但这个风险真实存在**——只要有两个文件谈 SKU，就会有人读错。**降低手段只能是首行强声明。**

**反方 5｜本库与既有 `共识性说明` 并存，本身就是"两处维护必然不一致"的开端，而 `02-2 §0.2` 已立过这条。**
**回应：反驳不了，接受。** 唯一缓解是**分工绝对化**：既有文档管"深"，本库管"浅"；本库不写定义、不写字段、不写法规依据，**凡要写深一律并入既有文档**。若将来本库出现第一条自写定义，即是越界，须当场纠。

**反方 6｜"库容"与"SKU"是两个特例——一个恰好未被覆盖、一个恰好已被覆盖。用这两个当试点，等于挑了两个最不会暴露问题的样本。**
**回应：成立。** 真正的考验在 `△` 词（分拨、移库/调拨/转移、订单履行），**那些词才见本库成色**。本轮未做，如实标注。
