## 一、SKU 的标准定义与层级关系

### 1.1 定义

**事实（B 级）**：

- SKU（Stock Keeping Unit，存货单元）是**库存管理中用于计量货物的基本单位**，同时指**指向该单位的唯一标识符或代码**。
  - 来源：维基百科 *Stock keeping unit*；百度百科「存货单元」词条（词条由"科普中国"科学百科词条编写与应用工作项目审核）
- 其属性是"**把所有该条目与其他条目区分开的属性集合**"。对产品而言，这些属性可包括：制造商、描述、材质、尺寸、颜色、包装、保修条款。
- **关键事实（必须记住）**：**「These identifiers are not regulated or standardized.」**——SKU 编码**不受规范约束、不被标准化**。
  - 维基百科原文：*These identifiers are not regulated or standardized. When a company receives items from a vendor, it has a choice of maintaining the vendor's SKU or creating its own.*
  - 百度百科同向：**「其编码规则由企业自主制定或沿用供应商标准，不受国际规范限制」**

**⇒ 推论 1**：**"SKU 的标准定义"里没有"标准编码"。** SKU 是一种**管理单元的定义方式**，不是一种**编码标准**。凡把 SKU 说成"国际标准编码"的说法，都是把 SKU 与 GTIN 混为一谈。

**⇒ 推论 2**：SKU 的**唯一性只在企业（或货主）内部成立**。这直接对应本项目 `memory\2026-09-15.md` 的裁定——**货品编码的唯一键是「（货主 × 货品编码）联合唯一」，不是全局唯一**。

### 1.2 与 GTIN / EAN / UPC 的分工（这是最容易混的一块）

| 编码 | 谁制定 | 作用范围 | 是否标准化 |
|---|---|---|---|
| **SKU** | **企业自己** | **企业内部**库存管理 | **否，不受规范** |
| **GTIN**（全球贸易项目代码） | GS1 | **全球**商品识别 | **是，国际标准** |
| **EAN**（欧洲商品编码） | GS1 | 全球零售条码（主要在北美以外） | 是，**GTIN 的特例** |
| **UPC**（通用产品代码） | GS1 | 北美零售条码 | 是，**GTIN 的特例** |
| **APN**（澳大利亚产品号） | GS1 | 澳大利亚 | 是，**GTIN 的特例** |

来源：维基百科 *Stock keeping unit*（原文：*This makes them distinct from Global Trade Item Number (GTIN), which are standard, global tracking units. The Universal Product Code (UPC), European Article Number (EAN), and Australian Product Number (APN) are special cases of GTINs.*）

**⇒ 推论 3（对本项目最关键）**：**厂商原码（UPC/EAN）标识的是"商品"，不标识"归属"。** 两个货主卖同一款货，货上贴的是**同一个码**。
→ 这**逐字印证**了 `memory\2026-09-15.md:118` 的判断：「厂商原码——标识的是**商品**，不标识**归属**。两个货主卖同一款货，货上贴的是**同一个码**」，以及 `:153` 的结论——**"扫得出商品、定不到货主"那一型依然存在，编码唯一规则解决不了它**。

### 1.4 层级关系：商品 / SKU / 店铺商品

**行业通行的四层**（合 B 级定义与 C 级实证）：

```
商品（Product / SPU）        ← 标品概念，同一个"东西"
   └── SKU（变体单元）        ← 颜色 × 尺寸 × 包装…… 每一个组合是一个 SKU
          └── 对外标识 / 平台 SKU（Listing 维度）  ← 店铺商品
                 └── 店铺（Shop / 站点）
```

要点：

1. **SPU 与 SKU 是"一 vs 多"**：同一款 pasta 三种规格 × 两种包装 = **六个不同 SKU**（C 级实证，意大利厂商案例）。
2. **SKU 是库存记账的最小单位**，不是商品的最小单位。**盘点盘的是每一个 SKU 的数量**，不是"商品"的总数。
3. **店铺商品（Listing）在 SKU 之外多一层**，因为它携带了 SKU 本身没有的信息：**挂在哪个店铺、哪个站点、卖什么价、什么包装形态**。
4. **同一件物理货，在不同店铺是不同的店铺商品**，但**在仓库里还是同一笔库存**。

**⇒ 推论 4（与本项目正面相关）**：层级里"店铺商品"这一层**不是库存的单位，是销售的单位**。这与 `01 §2.1.8` 的裁定同构：「**"货品"是仓内部的身份，"标识"是对外交付的身份，两者必须分开建模**」「**货在库里的时候，它没有平台身份**」。

## 二、批次管理与效期管理

### 2.1 为什么"必须落地"——必须分三层说，混在一起就是错的

你说的是"**必须**"。这个词必须拆开，因为三层的答案不一样。

#### 第一层｜法规层：对特定品类，是硬要求（A 级，可查证）

**食品**：

- **GB 14881-2025《食品安全国家标准 食品生产通用卫生规范》**（新发布）新增食品贮存与运输要求，明确：**「出货顺序应遵循"先进先出"或"近保质期先出"的原则」**；并规定**记录和凭证保存期限不得少于产品保质期满后六个月；没有明确保质期的，不得少于二年**。
- **上海市《网络食品交易仓储与提货点食品安全管理工作指引》**（政府文件）：
  - 第十七条：查验记录和凭证保存期限**不得少于产品保质期满后六个月**
  - 第十八条：贮存过程管理——**「（三）按近保质期食品先出库原则」**，无明确生产日期和保质期的生鲜食品遵循先进先出；**「（六）建立临近保质期食品预警机制，对临期食品明显标识、单独存放」**
- **贵阳市《食品经营者临近保质期食品管理工作指引》**：第十六条 **「先进先出、临期先出」**；并规定临期食品专区、处置流程（退货 / 销毁）。

**化妆品**（山东药监《化妆品生产许可有关事项》检查要点）：

- **第 66 条**：原辅材料、成品（半成品）及包装材料**按批存放**，标示信息须含 **批号、来料日期/生产日期、有效期（必要时）**
- **第 69 条**：企业应制定**产品保质期和物料使用期限的制度**，并建立**重新评估机制**
- **第 70 条**：**物料应按先进先出的原则**发放，并保存记录
- **第 73 条**：每批产品均应**按规定留样**，留样保存时间**至少超过产品保质期后 6 个月**

**⇒ 结论**：**对食品与化妆品类目，"批次 + 效期 + 先进先出/临期先出 + 记录留存"是法规义务，不是行业偏好。** 这是"必须"唯一站得住的含义。
**⇒ 反面**：**对普通日用品、印刷品、包材，没有任何法规要求批次效期。** 强行要求即制造无谓人工成本。

#### 第二层｜运营层：批次效期解决的是"不可逆错误"（推论，依据本项目自有规则）

依据 `01 §2.9.3` 的裁决规则——**校验强度按差错后果的不可逆程度分档**：

- **批次错的后果**：发错批次 → 无法追溯来源、召回时找不到货 → **不可逆**
- **效期错的后果**：过期品发到消费者手里 → 平台处罚 + 索赔 + 商誉 → **不可逆**
- 对比：**库位小差异、数量小偏差** → 盘点可纠正 → **可逆**

**⇒ 推论 5**：**批次/效期属于"不可逆"那一档，因此在启用的品类上必须强制校验。** 这不是行业经验，是从 `01 §2.9.3` 直接推出来的。

#### 第三层｜项目层：⚠️ 本项目的立场与"必须"相反，这里是硬冲突

**`01 §2.6` 的约束 6 标题原文：「批次效期天生"可管可不管"」。**

- `2.6.1`：**"是否管批次 / 效期 / 序列号"必须是「仓 × 货品」级配置**（v1 误写为"货品级"，已改错）
- `2.6.3`：**「未启用的货品，这些维度必须能"空着走"，不能被强制填写。」**

**⇒ 判定**：

| 层面 | 本项目立场 |
|---|---|
| **能力层** | **必须落地**——模型必须支持，**且一旦启用，先进先出 / 先到期先出必须自动生效，不能靠人记**（`01 §2.6.2`） |
| **业务层** | **不强制**——按「仓 × 货品」配置，未启用必须能空着走（`01 §2.6.1 / 2.6.3`） |
| **法规层** | **对食品化妆品是强制**（A 级事实），对本项目客户是否强制，取决于其货主卖什么 |

**⇒ 所以正确的表述是**：**"批次与效期管理是必须落地的能力，但不是必须启用的功能。"**
把你原话里的"必须落地"理解为"**能力必须落地**"——这一层我对；若理解为"**每个货品都必须管**"——**与本项目 `01 §2.6.3` 直接冲突，我不认。**

**红队（对立方案）**：主张"全部强制管批次效期，省得配置"。
**崩点**：`01 §1.3` 铁律——仓的利润 = 操作费 − 人工成本 − 差错成本。对印刷品货主强制扫批次，**每单多两次扫码，收益为零**（该品类无召回风险）。这与 `02-1 §3.5`「模型必须全、界面必须收」、`02-2 反方 3`「本域默认设计必须是"能不管就不管"」同一条逻辑。**否掉。**

### 2.2 批次管理要点

| # | 要点 | 依据 |
|---|---|---|
| 1 | **批次是"存放与追溯"的单位，不是"计价"的单位** | 批号、来料日期、生产日期须与实物同存（A 级：化妆品检查第 66 条） |
| 2 | **按批分开存放、分区储存，不同批次不得混放** | A 级：上海指南第 18 条、山东药监第 66 条 |
| 3 | **出库顺序规则须自动执行**（先进先出；有保质期则近效期先出） | A 级多条；`01 §2.6.2` |
| 4 | **批次必须能承接"来源"与"去向"**——进出双向可追溯 | `01 §2.1.2`（可回放对账） |
| 5 | **批次可空**：未启用批次管理的「仓 × 货品」必须允许无批次流转 | `01 §2.6.3` |
| 6 | **批次与库位是正交的**：同批次可分布多库位，同库位可存多批次 | `01 §2.1.1` 多维记录 |
| 7 | **记录留存期必须有下限**：食品类"保质期满后六个月"、无保质期者二年 | A 级（GB 14881-2025） |

**对第三点的一条硬提醒（事实，来自本项目对上游源码的实读）**：批次字段存在 **≠** 先进先出生效。`参考资料\若依WMS-项目分析.md` 记录——该项目 `advance` 分支有批次字段，但扣减 SQL **无 `ORDER BY expiration_date`、无 FIFO、service 层无效期拦截**。**"有字段"与"有管控"是两件事。**

| # | 要点 | 依据 |
|---|---|---|
| 1 | **效期不是登记，是预警机制**——须有临期阈值与告警 | A 级：上海指南第 18 条（六）"建立临近保质期食品预警机制" |
| 2 | **临期品须明显标识、单独存放** | A 级：上海指南第 18 条（六） |

### 2.4 二者不可互相替代（这是最常被混淆的一条）

| | 批次管理 | 效期管理 |
|---|---|---|
| 回答的问题 | **"这批货是哪次来的？"** | **"这批货还能卖多久？"** |
| 存在的目的 | 追溯、召回、来源归属 | 优先出库顺序、临期处置 |
| 有批次无保质期的品类 | 印刷品、包装材料（A 级：山东药监第 66 条对"有效期（必要时）"的措辞——**有效期是"必要时"才标**） | —— |
| 有效期货无批次的品类 | —— | 单一批次的短保生鲜 |

**⇒ 推论 6**：**两者是两个独立开关，不是"效期的前置依赖"。** 这与 `01 §2.6.1` 把三者（批次 / 效期 / 序列号）并列成**三个配置项**的做法一致。

## 三、标识颗粒度 与 SKU 的概念差异

### 3.1 概念差异（核心）

| | **SKU / 货品编码** | **对外标识** |
|---|---|---|
| 身份 | **仓库内部身份** | **对外交付身份** |
| 由谁定 | 货主自己定（或沿用供应商） | 平台 / 渠道 / 店铺分配，或卖家在该平台自定 |
| 是否标准化 | **否**（B 级事实） | 各平台自成体系，互不通用 |
| 数量关系 | 一个物理货品 = **一个**内部身份 | 一个货品 = **一组**对外标识（**多对多**） |
| 决定权 | 建档时确定 | **由订单决定**——货在库里时它没有平台身份 |
| 变了会怎样 | 追溯断裂（**不可逆**） | 贴错 → 平台仓扫不出 → **整批拒收**（不可逆） |

`01 §2.1.8` 的原文表述与上表完全一致：

> - **"货品"是仓内部的身份，"标识"是对外交付的身份，两者必须分开建模。**
> - 一个货品下挂**一组对外标识**，每条标识携带**归属（哪个平台 / 渠道 / 店铺）+ 编码值 + 适用规则**。
> - **货品与标识是"多对多"，且用哪一个由订单决定，不由库存决定。**
> - **标识挂在订单 / 发货单上，不挂在库存上**（至少不是常态）。

**⇒ 一个必须纠正的提法**：你说的"店铺商品需映射到**仓库库存 SKU**"——**方向对，宾语错。**
映射的对象是**货品（内部身份）**，**不是"库存"**。库存是「货主 × 仓 × 货品 × 批次/效期 × 库位 × 状态」的记录（`01 §2.1.1`）。把映射挂到库存上，等于让库存按平台拆账——而 `01 §2.1.8` 已明确排除这条路：**「这条直接排除"把平台 SKU 作为库存主键一部分"的做法——那样必然出现三笔库存，而货主入库时根本不知道这件货要去哪儿，拆了也建不出账。」**

### 3.2 「标识颗粒度」指的是什么

**颗粒度 = 一条标识要精确到哪一级归属。**

| 粒度 | 一条标识形如 | 建档成本 | 能否校验贴错 |
|---|---|---|---|
| **到平台** | 速卖通 → 编码 X | 最低 | 只能校验"是不是速卖通的码" |
| **到平台 + 店铺** | 速卖通 + A 店 → 编码 X | 中 | 能校验"是不是 A 店的码" |
| **到平台 + 店铺 + 国家站点** | 速卖通 + A 店 + 西班牙站 → 编码 X | 最高 | 最严 |

**这与 `01 §11.4` 的未决项 U19 同题**——01 已定"必须有这一层"，**粒度边界（平台 / 店铺 / 站点）尚未定，明确写了"需 Martin 给"**。

**⇒ 一条可给他参考的事实（B/C 级）**：**同一平台的不同国家站点，商品编码体系不一致**（速卖通有主站、俄罗斯站、西班牙站等多站点，海外仓实操中要求"确保 SKU 在各店的商品编码一致，否则系统无法识别共享库存"——**C 级来源，仅作线索，不作依据**）。
**⇒ 推论 7**：**若客户有多站点，粒度只到平台是不够的**——同一平台两个站点可以有各自独立的商品编码。但**这个推论依赖 C 级来源，须由 Martin 以业态事实确认**。

### 3.3 速卖通场景下的映射设计

**⚠️ 前置声明**：本节依据 `01 §2.1.8` 的结构（已定）给出设计，**不依据任何第三方平台的未经核实规则**。平台侧具体约束须以平台官方文档为准。

**前提三种关系必须先在数据结构上区分**：

| 关系 | 情形 | 映射基数 |
|---|---|---|
| **一对一** | 一个店铺商品 = 一个货品（最常见） | 1 : 1 |
| **多对一** | 同一货品被多个店铺 / 多个 listing 卖 | N : 1 |
| **一对多** | 一个店铺商品是**组套**，消耗多个货品 | 1 : N（走物料清单，`01 §2.10`） |

**C 级实证支持**：第三方 ERP 的字段设计中「平台 SKU：**需填写多个**，按 Enter 分隔」——**外部产品也按多对多处理，不是一对一**。

**设计要点**：

1. **映射表挂在货品下，不挂库存。** 结构：`货品编码 → [（渠道, 店铺, 站点?, 编码值, 适用规则）]`
2. **映射表是"可用的标识映射表"，不是"已贴好的标识"。** 它只用于**备查与校验**（`01 §2.1.8` 原文："货品下挂的是**可用的标识映射表**（备查、校验用），**不是"已经贴好的标识"**"）
3. **实际使用哪一个，由订单决定，不由映射表决定。** 映射表给的是**候选项**，订单给的是**选定项** —— 所以**发货单上必须固化"本次用了哪条标识"**，否则事后无法自证贴了哪个码。
4. **组套商品必须能映射到"货品或组套定义"**，不能只允许指向单个货品（否则捆绑销售无解）。
5. **映射必须双向可查**：从货品能查"它被哪些店铺商品引用"；从店铺商品能查"它指向哪些货品"。单向后一种是缺失的——**只做单向会导致下架时不知道影响谁**。

### 3.4 映射的维护机制（这一块最容易被漏，也最容易出事）

| # | 机制 | 理由 |
|---|---|---|
| 1 | **映射变更不得原地改**，须走"新增 + 失效"并留痕 | 同 `memory\2026-09-15.md:154`：编码一经使用不得改变指向；历史单据须能还原"当时指向谁" |
| 2 | **失效不得删除** | 删了则历史发货单的标识无法解释 |
| 3 | **店铺商品侧会单方面变更**（下架重上换 ID、平台改编码规则）→ 必须有**失效检测与重绑流程** | 上游不可靠是常态，`01 §2.5.4` |
| 4 | **一条货品允许"无有效映射"**——不能因无映射就拦住入库 | `01 §2.6.3` 同构逻辑；场景 1 异常分支"货品信息不全 → 建档兜底" |
| 5 | **不允许多条"同时有效且冲突"的映射指向同一（货品 × 店铺）**——须有唯一性约束 | 否则贴标时系统无法给出唯一答案 |
| 6 | **映射关系不可作为库存拆分的依据** | `01 §2.1.8` 已排除 |

### 3.5 与本项目文档的衔接（结论）

| 本文结论 | 对应本项目 | 状态 |
|---|---|---|
| SKU 内部身份 + 无标准编码 | `01 §2.1.6 / §2.1.8`；`memory 2026-09-15` 术语裁定 | 已定，**但 01 术语未落地（仍在混用）** |
| 标识多对多、挂订单不挂库存 | `01 §2.1.8` | **已定** |
| 标识粒度（平台/店铺/站点） | `01 §11.4` **U19** | **未决，待 Martin** |
