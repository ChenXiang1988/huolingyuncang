# 客户要求 · 记录与整理规则

> 本文件是这套方法的唯一说明。规则要改，改这里，改完在文末「版本」追加一行。

## 零、这套规则对付的是什么

Martin 收到的客户信息**不按格式来**：零散、无标注、可能没有客户名、口语、断句随意，直接丢过来。

所以这套规则的第一目标**不是记得漂亮**，而是两件事：

1. **原始的不丢**——客户说过的话必须能原样找回。
2. **我加的不混进去**——我的一切理解、压缩、推断，都不能伪装成客户的原话。

### 三条底线

| 编号 | 底线 |
|---|---|
| 一 | 原文原样留底，**一字不改** |
| 二 | 整理出来的东西是**衍生物**，每一条都能回到原文某一段 |
| 三 | 原文没说的，**不许补** |

## 一、两类提出方与目录结构

### 1.1 两类提出方（2026-09-25 定：两层都会提，两层都记）

| 代号前缀 | 是谁 | 与本项目的关系 | 他会关心什么 |
|---|---|---|---|
| **运营** | 云仓运营者 | **买方**。`CODEBUDDY.md §一` 的目标客户 | 成本、效率、少出错、能对账、能收上钱 |
| **货主** | 云仓的客户 | 把货托管出去的那层 | 我的货别丢别损、库存准不准、我自己要不要出人出力、我的数据别人看不看得见 |

依据 `CODEBUDDY.md §一`：本项目是「一仓 N 货主，货权分离」，所以**这两层同时存在于任何一个仓里**。

### 1.2 硬性预判：跨层对立是常态，不是异常

两层人站在同一件事的两面，说出来的要求**经常方向相反**，这是结构决定的，不是我记录得不好。

**本项目已经出过一次这类对立的结构形态**（事实，可复核）：

- `02-2 §4.2.4 库位级隔离`——库位带「归属货主」，存储类库位必填归属，上架直接拦。服务的是**隔离**。
- `02-2 Q7「利用率收益归谁」`——服务的是**利用率**。

两条在同一份文档里并存，且隔离的代价（库位切碎、利用率下降）已记录在案、由 Martin 接受。
**这两条是不是货主提出的，我不确定——标为推断。** 我确定的是它们服务的方向相反。

### 1.3 归档纪律（三条）

1. **不按"谁掏钱"给记录排序。** 运营者是买方，他的话在商业上更硬，但**排序就是裁决**，裁决不在这一层。记录层只负责把层级标清楚。
2. **输入里没标明是谁说的 → 进「待归属」，不猜。** 猜错层级比不知道更糟。
3. **一条要求同时涉及两层时，记两条，各标各的层级，互标对立关系。**

### 1.4 目录结构

```
客户调研/
├─ 00-记录与整理规则.md          ← 本文件
├─ 原始输入/                      ← 按天一个文件，当天可追加，跨天不改
│   └─ YYYY-MM-DD.md
├─ 整理稿/
│   ├─ 待归属.md                  ← 没说清是谁说的
│   ├─ 运营-001-客户简称.md       ← 云仓运营者（买方）
│   └─ 货主-001-客户简称.md       ← 云仓的客户
└─ 跨层对立与缺口.md              ← 只列对立与缺口，不做裁决
```

**目录按需建，有内容才建，不预建空壳。**（依据 `CODEBUDDY.md §六`：不建非必要目录与脚手架）

**两个命名空间分开的好处**：运营者和货主即使同名、同城、同行业，也不会撞到一起；且目录排序时两类自动分开，一眼能看出每层的声量。

## 二、两条管道的分工

| 层 | 谁写 | 能不能改 | 作用 |
|---|---|---|---|
| **原始输入** | 我，照抄 | **不能** | 唯一真相来源 |
| **整理稿** | 我，加工 | 可追加 | 便于阅读的**视图**，不是新的真相 |

**关键：整理稿与原始输入冲突时，一律以原始输入为准。**

这一条是整套设计的承重墙。没有它，我一旦理解错，错误就再也查不出来——因为我的整理稿读起来比原文更顺，更像真的。

## 三、原始输入的落盘规则

- 按天一个文件：`原始输入/YYYY-MM-DD.md`
- 每次投喂**追加**一段，段落头是投喂时间：

```
## 14:32

（原文照抄，一字不改。错别字、语气词、口语、断句、标点、表情符号，全部保留。）
```

- **一天内允许追加；过了当天不再改动。**
- 当天要更正早先的内容：在文件**末尾**追加一段「更正」，写明更正的是哪一段。不回改上文。
- 不知道是谁说的、或者明显是转发内容：**照抄，不猜**。

## 四、整理规则

### 只做四件事

| 动作 | 说明 |
|---|---|
| **分条** | 把一段话切成一条一条的要求，编号 `运营-001-03` / `货主-002-05`（主体编号 - 条目序号） |
| **去重** | 同一句话说了两遍，并成一条，两处出处都标 |
| **归类** | 挂主体、挂主题（收货／上架／拣货／复核／出库／盘点／计费／其他） |
| **标来源** | 每条必标它属于哪一级（见下） |

### 来源等级（三选一，不许含糊）

| 等级 | 含义 | 判据 |
|---|---|---|
| `原话` | 客户原话直录 | 原文里能**逐字**找到 |
| `转述` | 我把口语压成书面话 | **语义不变**，只换说法与语序 |
| `推断` | 我的判断 | 正文里**必须出现「推断」二字** |

### 绝对不做

1. **不补原文没有的名词、数字、因果。**（"因为…所以…"这类连接必须是原文里本来就有的）
2. **不调和矛盾。** 两句话打架，两条都留，标关系，不判谁对。
3. **不判优先级、不判可行性、不判要不要做。**
4. **不把行业常见做法写成客户说的。**（`CODEBUDDY.md §2.2.9` 已犯四次）
5. **不因为谁是买方就把他的一句记成十条、把货主的十条压成一句。** 声量必须忠实于原文，不服从商业权重。

### 可检验判据

> **整理稿每一条的正文里，每一个名词，都应该能在原始输入里找到出处。找不到的，要么删掉，要么标「推断」。**

这条是可核对的。Martin 可以随便挑一条，我当场指出它在原文哪一段——指不出来，那条就是编的。

## 五、整理稿的条目模板

```markdown
### 运营-001-03

- 摘要：        一句话（用原文的词，不用行业词替换）
- 出处：        原始输入/2026-09-25.md · 14:32 段
- 来源等级：     原话 / 转述 / 推断
- 提出方层级：   运营者 / 货主 / 未标明
- 归属关系：     他的货（或他的仓）与谁相关——只有原文提到才写，没提留空
- 涉及环节：     他只提到的环节；没提就留空
- 措辞：        原话里的强度词（"必须""最好""能就行""现在凑合"），照录
- 关系：        同层冲突 / 跨层对立 / 文档冲突（三种见下），互标条目编号
- 缺口：        原文没说清的点——**只写问题，不写答案**
```

### 「关系」栏的三种取值（只标，不裁）

| 取值 | 含义 | 例子 |
|---|---|---|
| `同层冲突` | 同一个人前后两次说法打架 | 上次说批次必须管，这次说管不管都行 |
| `跨层对立` | 运营者与货主的方向相反 | 见 §1.2 的库位隔离 / 利用率 |
| `文档冲突` | 与 `设计文档\` 已落盘条款打架 | 客户要的东西与 `01` 或 `02-2` 的定条款直接相反 |

**`文档冲突` 是最值钱的一类**：它说明要么我们的设计错了，要么这个客户不是我们的客户。**这两件事都不由我判。**

### 字段说明

- **摘要**是给人扫的，**出处**是给人查的，两个都在才叫可追溯。
- **措辞**栏保留他说话的语气强度——日后不必靠回忆判断他当时有多想要。
- **关系**栏只做指针。裁决不在这一层，在 Martin 手上。
- **缺口**栏是唯一允许我提问题的地方，且**只许提问题**：一旦我开始填答案，就变成了推断冒充事实。

### 整理稿文件头（每份开头固定一段）

```markdown
- 提出方：     Martin 输入时用的叫法（原样照录）
- 层级：       运营者 / 货主 / 未标明
- 首次出现：   2026-09-25
- 本文件性质：  整理稿（视图）· 与「原始输入」冲突时以原始输入为准
- 归属关系：    与哪些仓／哪些货主相关（只有原文提到才写）
```

## 六、缺口清单：把「不够细致」变成主动产出

整理完一批，对照下面八问扫一遍。缺哪项，列进 `跨层对立与缺口.md`，等下回有机会再问。

1. 谁在做、用什么做、一天做多少次？
2. 上次出事是什么时候、出在哪个环节、当时怎么处理的？
3. 有没有外部要求压着（平台规则、客户合同、监管）？
4. 只能先改一个的话，先改哪个？
5. 有没有"这也得能做"的情况？（异常分支通常藏在这句后面）
6. 他的下游怎么看这件事？（问运营者就问他的货主，问货主就问他的上游）
7. **涉及不涉及数量口径（件／个／箱／米／公斤／桶／卷）？**
8. **这句话谁说的——运营者还是货主？他管着几个仓／他的货放在几个仓？**

第 7 问是本项目专用：`设计文档\` 已确认托管对象含**连续量与主辅单位换算**，而现有文档里的数量**全是整数单位**（`小数` `桶` `卷` `液态` 在 5 份文档中零命中）。客户一句话里有没有量词，直接决定这个要求落在哪个坑里——这不是细节，是分岔口。

第 8 问是第 1.3 节的落地：**层级标不出来，这条记录的实际价值会掉一半**，因为读的人没法判断该往哪个方向用。

## 七、往外走的路（本文件夹之外）

**本文件夹里的东西，不进任何交付物。**

要把客户的话变成产品依据，必须经过 Martin 本人判断，写成可落盘的断言，才进 `参考资料\` 或 `设计文档\01`。

依据：`01:127` 规定后续交付物必须能从 01 推出来；而客户原话是**事实主张**，不是**业态事实**。中间那一步转译，系统不能替他做，也不该替他做。

## 反方审查

**1. 「按天一个文件、当天可追加」会毁掉原始性，因为追加本身就是改文件，改过多少次、改掉了什么，事后无从追溯。**

→ 部分认账。追加段落带时间戳，只能说明"加了什么"，不能证明"没删什么"。**没有规避手段，除非每个文件写一次就封存。** 已在未决项列出，请 Martin 选：要么接受这个风险换便利，要么改成"每次投喂一个文件"（代价是文件数量爆）。

**2. 「来源等级三选一」在实操上会塌，因为"转述"与"推断"的界线在口语压缩时永远是模糊的，而我会本能地往低风险档填（填"转述"而不填"推断"）。**

→ 修正已加：§四「可检验判据」把主观分档改成可核对的动作（每个名词能否在原文找到出处）。**但这只是把模糊从"等级"挪到"名词"，没有消除模糊。** 接受。

**3. 这套规则挡不住最大的风险：我为了让输出通顺而把断裂处填平，因为语言模型的默认行为就是补全，而补出来的东西和原文一样自然。**

→ 修正：§四「绝对不做」第 1 条 + 可检验判据。**但这是约束，不是保证。** 对冲只能靠抽查——你随便挑一条，我指原文给你看。指不出来就是编的。

**4. 「冲突只标不裁决」会积累成一堆无法使用的对立条目，因为两边的话本来就互相顶，不裁决就永远收敛不成一条需求。**

→ 认账，但这是刻意的：裁决的活儿不属于记录层，属于你。**规则里写"本层不裁决"，不等于"不用裁决"** —— 这条得说清，否则会读成"矛盾放着不管"。

**5. 按人分整理稿的前提是"信息里带标识"，而你已经明说输入不按格式来，那么大概率大批信息落进「待归属」，整理稿形同虚设。**

→ 修正：允许先按**主题**归档作为临时容器，身份明确后归位；**不许我猜。** 已写进 §1.4。

**6. 这套规则的成本全在我这边、收益在你那边，你没有任何办法判断我有没有偷工，因为你不会去逐条核原文。**

→ 认账，这是本方案最弱的一环。唯一的对冲是抽查机制。**如果你从不抽查，这套规则的实际强度等于零。**

**7. 「两层都记、但不排序」会把价值结构搞反，因为运营者是掏钱的，他一句"我要这个"比货主十句更硬；规则禁止排序，等于把硬约束和软诉求平铺在一起，读的人得自己重排一遍。**

→ 认账，且这是刻意的：排序就是裁决。**但记录层必须提供足够的分辨信息，让排序成为可能**——所以「提出方层级」「措辞」「关系」三栏一个都不能省。**这三栏不是装饰，是让排序可行的最低配置。**

**8. 「按人归档」在货主数量上来之后会直接崩，因为目标客户画像是「20 仓 / 上百货主」，上百份货主整理稿读不动，而你没法预先知道该建哪些。**

→ 修正：**货主文件只在 Martin 实际投喂到时才建**，不预建全量；未标明身份的一律进「待归属」。**但量级真上来时，本方案迟早要从"按人归档"换成"按主题归档"。** 已列未决项 7。

## 未决项

1. **原始输入的封存方式**——按天可追加（便利，弱保护）／每次投喂一个文件（强保护，文件多）。见反方 1。
2. ~~「客户」指哪一层~~ → **已定（2026-09-25 11:29）：两层都记。** 新问题：**整理稿的主键是按人，还是按「人 × 仓」？**（一个货主可能同时用几个仓，一条要求可能只针对其中一个仓）
3. **涉密处理**——某次输入含客户名单、价格、合同时，要不要单独标记并隔离存放？（本工作区已实测无版本库、无忽略文件，风险来自人工复制外发，不是自动同步）
4. **是否需要「客户名录」索引**——它是唯一会被反复修改的文件，与"不可改"原则相冲。暂不建。
5. **裁决出口由谁承担**——见反方 4，这一层不裁决，那谁来裁、在哪裁。
6. **跨层对立出现后怎么用**——是拿去跟运营者谈，还是直接改产品设计？**这两种用法对记录格式的要求不同**，现在定不了，等第一例真对立出现再定。
7. **货主数量上百后，按人归档是否还成立**——见反方 8。
