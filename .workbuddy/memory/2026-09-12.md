- **方法教训（重要，已写进 01 与记忆）**：**红队机制不能替代业态事实。** 反方 19 里那个"模拟的云仓运营者"是我编的，它编错的时候比没有红队更危险——**给错误观点披上了"对立面已受检验"的外衣**。红队的价值是逼出对立面，不是生产事实。
- **Martin 给的理由为什么成立**：加工方向**由订单决定**（发 TEMU / SHEIN / Amazon 的要求各不相同），而**入库时不知道这件货要去哪儿**。
- **重大推论（连带面很大）**：
  1. **库存必须以"未定向的通用形态"持有**——库里不该有"TEMU 的货"与"SHEIN 的货"两笔账。
  2. **标识挂在订单上，不挂在库存上**（2.1.8 修正）；货品下挂的是**可用映射表**，不是"已贴好的标识"。
  3. **出库时才加工 ⇒ 加工与发货几乎同时 ⇒ 库存账上不需要长期保留"加工态"**——模型大幅简化，v9 设想的"可用量必须分状态统计"在默认形态下**并不需要**。
  4. **唯一例外是预先加工（定向备货）**——此时才出现"定向库存"，反方 17 的问题才真正成立。
- **结构改动**：
  - **场景 7「复核与打包」扩充**：节点变为 复核 → **出库加工（按订单定向：套袋 / 贴平台 SKU 标签 / 换包装）** → 装箱 → 称重 → 贴面单。
  - **6.2 出库主干**流程图加入「出库加工」节点，并新增判定点"本单是否需要出库加工（按平台规则）"。

  - **2.10.7 重写**：主形态 = **按单现场加工**；预先加工 = 例外，且明确代价（**定向库存是对通用性的一次消耗**——平台单没来/改规则/量估错，货就砸手里）。与组套备货式的关键差异：套装本来就是独立可售商品，定向库存不是。
  - **区分「平台 SKU 标签（商品标）」与「面单（物流单）」**——一个贴商品、一个贴包裹，位置与依据都不同。§9.1 新增"平台合规规则"对接行。
