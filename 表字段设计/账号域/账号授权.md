# 账号授权

**日期**：2026-09-26

> **本表是权限的唯一真相。** `角色` / `角色动作` 只是勾选时的模板；权限一旦落到本表，**与推出它的角色无关**（`02-5` §4.3、推 4）。

## 枚举取值

- **来源标记**：`角色预设` · `手工追加`

## 键与索引

- **主键**：授权标识
- **唯一**：账号标识 + 仓库标识 + 动作标识
- **外键**：账号标识 → 账号；仓库标识 → 仓；建档人 / 更新人 → 账号
- **索引**：账号标识（登录时取该账号的全部授权）· 仓库标识
- **被引用**：无

## 说明

1. **「仓库标识可空」是本表最要紧的一处设计。** `01` §4.3 v2 只说"动作授权要与「仓」绑定"，**没说必须绑**。本端的定位是**跨仓统筹**，"查看经营看板"这类动作没有单一的仓可绑。⇒ 用**可空**表达全局动作，**一张表、一套唯一键、一处界面**（`02-5` §4.3，推 5，列 E5）。

   **反方案（路乙）**：绑仓授权一张表、全局授权一张表。**否掉**——两张表会让"同一动作在 A 仓绑仓、在 B 仓全局"变成不可能，而条例上并无禁止。

2. **本表就是「账号 × 仓 × 动作」三元组**，`01` §4.3 与 §4.1 v2 两句合读的结果（`02-5` 推 2，强度**强**）。

3. **本表不存数据可见范围。** `01` §2.1.4 明写"越权处置必须在**模型层面不可表达**，**不是靠权限拦截**"、§2.4.1 要求"隔离进模型底层"。⇒ **本表只管"能不能执行这个动作"，不管"能看到谁的数据"**（`02-5` 概念对 2，**红线**）。若某处的数据隔离是靠本表实现的，**那里就写错了**。

4. **本表不设「生效 / 失效时间」。** `01` 零依据；且权限过期与离职是同一件事，用 `账号.状态` 的停用表达即可（`02-5` §6.3 判断 1，列 E5）。

5. **本表不设「授权人」字段。** 它会让"谁给的权"变成一条链，而链的尽头（第一个系统管理员的权是谁给的）答不了。⇒ 改用**事件**记录（账号操作日志，**尚未建**，`02-5` E3，见 §6.3 判断 2）。
