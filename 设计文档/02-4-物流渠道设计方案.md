## 一、为什么单独做这一域

### 1.1 渠道不是一个字典表，是三条业务链的公共锚点

| 链 | 渠道在其中的角色 | 依据 |
|---|---|---|
| **拆单** | 渠道约束（限重 · 限体积 · 限金额）可能是拆单第二把刀的**阈值来源** | `01` §7.10（推 4，列 V7） |
| **集包与交接** | **集包单按渠道**归集：多张出库单的包裹 → 1 张集包单 | `01` §6.5 |
| **面单** | 面单来源两档（云仓打印 / 货主提供）挂在渠道上；1 箱 : 1 面单 | `01` §9.1 + §6.5 |

**这三条链在 `01` 里各自成立，但它们在模型上共用一个对象。** 不把它单独立出来，实现者会在三处各建一份字段。

### 1.2 目标挂接

| 目标 | 本域的贡献 |
|---|---|
| A 不可逆错误 | **间接**——"渠道缺失"是可定位的异常（`01` §7.3），但渠道本身不防错 |
| B 时效 | **间接**——渠道是时效的实际承载者；**但渠道级时效与「货主 × 仓」级承诺的关系需先定（V4）** |
| C 成本 | **无正贡献**。渠道域本身不省人工 |

> **诚实交代**：本域对三个目标**没有一个直接贡献**。它的存在理由是"出库链离不开它"（三条锚点），**不是"它自己值钱"**。反方 1 会拿这一点打。

## 二、概念定义

### 2.1 「承运商」与「物流渠道」是两层

**`01` 只出现「承运商」与「渠道」两个词，没说它们的关系。** 本项目按两层建：

```
物流承运商（顺丰速运）          ← 外部法人，全局
   └── 物流渠道（顺丰标快 / 顺丰特惠）   ← 可揽收口径，仓级
          └── 约束：限重 / 限体积 / 限金额
```

**为什么必须两层**：约束挂在渠道上（`01` §9.1 明写），而**同一承运商的不同产品限重必然不同**。**若只有一层，承运商名就要在每条渠道里重复填，且无法回答"这家承运商在本仓有哪些渠道"。**

> **术语对齐（重要）**：**本项目用「物流渠道」，不用「物流产品」。** 需求侧口头常称"物流产品"，指的就是本文的「物流渠道」——**它是承运商下的一个可揽收口径，不是独立的商业产品**。**本文件全篇统一用「物流渠道」。**

### 2.2 概念清单

| 概念 | 定义 | 作用域 |
|---|---|---|
| **物流承运商** | 提供运输服务的**外部法人**。如顺丰速运、中通快递 | **全局**（推 3） |
| **物流渠道** | 某承运商下的**一个可揽收口径**，携带约束与揽收方式。如顺丰标快 | **仓级**（`01` §9.1，推 2） |
| **渠道约束** | 限重 / 限体积 / 限金额——**渠道级** | 随渠道 |
| **揽收方式** | 该渠道**能不能**上门揽件（能力集） | 随渠道 |
| **交付方式** | **本次出库**选送站点还是等上门 | **出库预报单**（`01` §9.1 明写） |
| **面单来源** | 云仓打印 / 货主提供（两档） | 随渠道 |

### 2.3 三个容易混的概念对

**概念对 1｜承运商 vs 物流渠道。**
承运商是法人，渠道是产品口径。**约束挂渠道、不挂承运商**。推论两条：**停用承运商 ⇒ 其下全部渠道一并停用**（级联）；**停用渠道不影响承运商**。

**概念对 2｜渠道的「揽收方式」 vs 预报单的「交付方式」。**（缺口 1）

| | 渠道 · 揽收方式 | 预报单 · 交付方式 |
|---|---|---|
| 回答 | 这个渠道**能不能**上门揽件 | 这一单**要不要**上门揽件 |
| 性质 | 主数据（云仓维护，长期） | 单据属性（货主给定，逐单） |
| 取值域 | 上门揽件 / 送指定站点（**能力集**） | 送指定快递站点 / 承运商上门揽件（**本次选法**） |
| 谁定 | 云仓 | 货主（`01` §9.1 明写"不是仓的自由裁量"） |

**本文的处理**：两者都保留，并加一条关系——**预报单选的交付方式必须落在该渠道的揽收方式能力集内**。违反时**允许后补**（不阻断提交，转单据处理异常，见 L7 与 §5.2）。**这条关系是本文推的（V3）。**

**概念对 3｜面单来源 vs 面单模板。**
「来源」是**两档枚举**（云仓打印 / 货主提供），本文放这一档口。**「模板」是对接物**，属 U6（已移交 `03`），**本文一个字不做**。

## 四、功能设计

### 4.1 承接块：对 02-1 的增补

**只有一处**：**声明"渠道的宿主是仓"**——渠道是仓级主数据（`01` §9.1），因此它引用 `02-1` 的仓，**但本文不改 `02-1` 的仓字段清单**。

> **为什么不给仓加一个字段**：`01` §9.1 把渠道定义成**独立主数据**（"渠道编码"是它自己的键），不是仓的一个属性。**做成仓表的一列会立刻撞"一仓多渠"**——与 `02-1` §1.5「属性下沉规则」同一条逻辑：**同仓内可能有多条 → 下沉成子表。**

### 4.2 承运商档案

**维护方**：云仓管理端（`01` §9.1 只说渠道由云仓维护；**承运商的维护方 `01` 未表态**，本文按"与渠道同源"推定，列 V1）。

**字段**：见 §6.2 实体①。

**校验**：

- 承运商编码唯一。
- **停用承运商 ⇒ 级联停用其下全部渠道**（概念对 1）。
- **不允许删除仍被渠道引用的承运商**（对齐 `02-1` §2.2 第 1 项"仓编码一经使用不得更改"的精神）。

### 4.3 物流渠道配置

**维护方**：云仓管理端。

**字段**：见 §6.2 实体②。

**校验清单**：

| 编号 | 规则 | 违反时 |
|---|---|---|
| **L1** | 渠道编码唯一。**唯一域＝全局还是承运商内，列 V6** | 拒绝保存 |
| **L2** | 所属仓必填（作用域＝仓级） | 拒绝保存 |
| **L3** | 所属承运商必须为「启用」 | 拒绝保存 |
| **L4** | 约束三项（限重 / 限体积 / 限金额）**至少填一项** | 拒绝保存。**理由**：三项全空则对拆单无任何约束力，等于一条只带名字的渠道——**要么填、要么明确它不作约束** |
| **L5** | 面单来源必须二选一 | 拒绝保存 |
| **L6** | 停用的渠道不得被新增的预报单选中 | **预报单侧直接拦截**（对齐 `02-1` §3.3 C3b"上架环节系统直接拦截"的精神） |
| **L7** | 预报单的交付方式必须落在该渠道的揽收方式能力集内（概念对 2） | **允许后补**——不阻断提交，转单据处理异常（§5.2） |

> **L7 为什么是"允许后补"而不是"拒绝保存"**：依据 `01` §7.5「校验强度按**差错后果不可逆程度**分档」。"交付方式与渠道不匹配"是**可逆**的——货还没动，改预报单即可。**真正不可逆的是发错渠道导致的面单费与时效损失，而不是这个选择动作本身。**

### 4.4 渠道约束如何喂给拆单（承接 01 §7.10）

`01` §7.10 的两把刀：

| 刀 | 来源 | 与本文的关系 |
|---|---|---|
| 第一把：不可混装 | 全局约束（品类互斥矩阵） | **无关**。`02-1` §2.3 v12 补充已声明它不参与继承与例外机制 |
| 第二把：金额 / 体积 / 重量阈值 | **可配** | **本文尝试提供来源**：渠道约束三项（推 4） |

**接口定义（本文给的，待 V7 裁定）**：

```
拆单阈值 = f(渠道约束, 仓级阈值默认值)
```

**但两者的优先关系 `01` 没写**——是"渠道约束覆盖仓级默认"，还是"两者取严"？**列 V7，本文倾向"取严"（小的一方生效）。**

> **诚实交代**：推 4 是本域与拆单域之间**最强的一个假设**。若 Martin 判为"拆单阈值与渠道约束无关、另有来源"，则**§4.4 整节失效，渠道约束退化为纯提示信息**。反方 3 是这条的加强版。

## 五、核心流程

### 5.1 货主选渠道（预报单侧，云仓不参与）

```
货主端：创建出库预报单
   → 选仓（货主决定，01 §6.5）
   → 系统给出该仓的渠道候选集（候选集来源见 V2）
   → 货主选渠道 + 交付方式（送站点 / 等上门）
   → 提交
```

**云仓端的角色**：只**校验放行或转人审**（`01` §6.5），**不参与选渠道**。

### 5.2 渠道缺失 → 单据处理异常

**触发条件（本文给的判定）**：

| 情形 | 是否算"渠道缺失" |
|---|---|
| 预报单未指定渠道 | **算** |
| 指定的渠道已停用 | **算** |
| 指定的渠道不属于该仓 | **算** |
| 交付方式不在该渠道的揽收能力集内 | **算**（L7） |
| 货主自带面单，且快递公司不在该仓渠道主数据内 | **算**——但这五件事属 U29，**本文不给定论** |

**处置**：进单据处理异常台账，**责任人＝云仓端单据岗**（`01` §7.3 明写），**只改单据状态、不回写库存**（货还没动）。**"原因 / 闭环时限"沿用 U28 的待定状态**，本文不新造。

### 5.3 集包按渠道

```
N 张出库单的包裹 ──（按渠道归集）──→ 1 张集包单 ──→ 交接单
```

**模型上只需要一点**：包裹所属的出库单带渠道，集包时按渠道分组。**本文不重画这条链**（`01` §6.5 已定）。

## 六、关键数据模型

### 6.1 模型总览

```
物流承运商 ──1:N──→ 物流渠道 ──N:1──→ 仓（02-1 §2.2，不重复定义）
                      │
                      ├── 约束：限重 / 限体积 / 限金额 ──→ 拆单阈值（01 §7.10，V7）
                      ├── 揽收方式 ─────→ 校验预报单的交付方式（L7）
                      └── 面单来源（两档）
```

**基数**：承运商全局共享；渠道**每仓一套**。**注意量级**：若每仓 8 条渠道，20 仓即 160 条渠道记录——**远小于 `02-2` 的配额量级（上千组）**，不构成配置负担（反方 4）。

### 6.2 实体与字段

> **只列本域新增的两个实体。** `02-1` 的仓、区域、库位字段**一律不在此重列**。

**① 物流承运商**（新建实体；**`01` 无任何字段，全为本文推**）

| # | 字段 | 类型 | 必填 | 说明 | 来源 |
|---|---|---|---|---|---|
| 1 | 承运商编码 | 字符串 | 是 | 唯一标识 | 推（同 `02-1` 仓编码的处理） |
| 2 | 承运商名称 | 字符串 | 是 | 如"顺丰速运" | 推 6 |
| 3 | 简称 | 字符串 | 否 | 列表与面单用的短名 | 推 |
| 4 | 揽收联系人 / 电话 | 文本 | 否 | 上门揽件的对接人。**与 U29"谁约揽收"相关，本文只留位** | 推 |
| 5 | 启用状态 | 枚举 | 是 | 启用 / 停用；**停用级联其下渠道** | 推 5 |
| 6 | 备注 | 文本 | 否 | — | 推 |

> **本文刻意不设的**：**统一社会信用代码 / 开户行 / 结算账号**。**理由**：仓与承运商之间**未必有结算关系**（可能是货主自行结算），这三项属商务且 `01` 无依据。**若 Martin 判为需要，与 V1 一并处理。**

**② 物流渠道**

| # | 字段 | 类型 | 必填 | 说明 | 来源 |
|---|---|---|---|---|---|
| 1 | 渠道编码 | 字符串 | 是 | 唯一标识（唯一域见 V6） | **`01` §9.1 直给** |
| 2 | 渠道名称 | 字符串 | 是 | 如"顺丰标快" | **推 6** |
| 3 | 所属仓 | 引用 | 是 | 指向 `02-1` 的仓 | **`01` §9.1「仓级」** |
| 4 | 所属承运商 | 引用 | 是 | 指向实体① | **`01` §9.1 直给** |
| 5 | 限重 | 数值（可空） | 条件 | 单件上限 | **`01` §9.1 直给** |
| 6 | 限体积 | 数值（可空） | 条件 | 单件上限 | **`01` §9.1 直给** |
| 7 | 限金额 | 数值（可空） | 条件 | 单件上限 | **`01` §9.1 直给** |
| 8 | 揽收方式 | 集合 | 是 | 上门揽件 / 送指定站点（**能力集**，可多选） | **`01` §9.1 直给** |
| 9 | 面单来源 | 枚举 | 是 | 云仓打印 / 货主提供（**两档**） | **`01` §9.1 直给** |

> - **时效承诺**——与 `01` §7.2「货主 × 仓」级承诺的关系未定（V4）；
> - **服务区域**——`01` 无依据，**我编不出**；
> - **限件数**——同上。**它曾出现在我最初的方案里，复核后删除：没有任何 `01` 依据，加它就是编。**
>
> **这三项若要做，必须是 Martin 给的，不是我推的。**

### 6.3 三个模型判断

#### 判断 1｜承运商独立成实体，而不是渠道上的一个文本字段

**对立方案（红队）**：`01` 原文就是"渠道编码 / 承运商"，**照抄一行文本最省**，不需要新实体。

**为什么否掉它**：一旦承运商是自由文本，同一家承运商在 20 个仓、160 条渠道里会出现"顺丰""顺丰速运""SF"三种写法，**而"这家承运商在本仓有哪些渠道"这个问题就答不了**——它需要一个稳定的键。**这与 `02-1` 拒绝把"仓库类型"做成自由文本是同一条逻辑：可枚举的东西必须有字典，自由文本必然退化。**

**但承认代价**：多一张表、多一层维护。**若 Martin 判为承运商不需要独立档案（V1），则 §6.2 实体① 整体删除，渠道第 4 项退化为文本字段。** 这条我留了口子。

#### 判断 2｜渠道挂仓，不挂「仓 × 货主」

**`01` §9.1 说"仓级主数据"，没说是否按货主区分。** 本文按**纯仓级**建。

**为什么**：`01` §9.2① 明写"作用域＝仓级"。**若做成「货主 × 仓」级，20 仓 × 上百货主 = 上千条渠道配置**——这正是 `02-2` 反方 1 已踩过的坑。**渠道是仓的物流能力，不是给某个货主的定制。**

**但候选集可能按货主过滤**（V2）——**过滤是查询层的事，不是模型层的事**。这一区分很重要：**模型上仓级、界面上按货主切**，与 `02-2` §4.2.4.3 的"可按货主切片"同一路数。

#### 判断 3｜承运商全局、渠道仓级——两者作用域不同，不能合并

**红队**：为什么不把承运商也做成仓级，一张表更简单？

**因为承运商是外部法人**：同一条顺丰在 20 个仓是同一家顺丰。**做成仓级会让"本集团一共用了多少家承运商"答不了**，且联系方式改一次要改 20 处。

**但承认延伸问题**：承运商全局共享意味着**它被所有仓共用**——**在多租户场景下可能过宽**。**本项目的部署形态是私有化单实例（`01` §1.4 + `CODEBUDDY.md` §一），不跨客户，故此问题不存在。**

## 九、反方审查

### 反方 1｜这一域是"为了接住 01 的一句话"而建的，它自己不产生价值

**站在一个评估交付范围的立场上**：`01` §9.1 只给了九个词，你扩成两个实体、两个页面、一套校验。**这九个词不建表，出库链就转不动吗？** 转得动——**渠道完全可以先做成出库单上的两个文本字段（承运商 + 渠道名）。**

**回应：前半接受，后半不接受。**
- **前半接受**：本域对三个目标没有一个直接贡献（§1.2 已诚实交代），**它不是"值钱的功能"，是"不得不有的底座"**。
- **后半不接受**：文本字段会让**拆单阈值无处安放**（`01` §7.10 明说阈值可配，可配就得有配置宿主），且**"渠道缺失"这条异常判定不了**（`01` §7.3 点名了它）。**要接这两条，就必须有表。**

**红队（对立方案）**：如果 V7 判为"阈值不从渠道来"，**本域的价值就只剩"渠道名有一处统一维护"**——那时它确实可以先做文本字段。**这条取决于 V7，我把它交给 Martin。**

### 反方 2｜"承运商全局、渠道仓级"这个切法会造成维护上的精神分裂

**站在一个 20 仓运营者的立场上**：我在第 3 个仓新建一条"顺丰标快"，但承运商已经在第 1 个仓建过了——**系统是让我复用，还是让我再建？** 如果复用，那"某仓的渠道清单"就是全局渠道的一个子集；如果各建各的，那承运商全局共享就没意义。

**回应：接受，这是真实的歧义。** 本文的立场是**复用**（承运商全局、渠道按仓引用它），但**"新建渠道时承运商下拉里出现哪些"这条交互细则没有给**——它属 V1 的连带问题。**我承认 §6.1 的模型图把这一层画得太干净了。**

### 反方 3｜推 4（渠道约束＝拆单阈值来源）是整个设计里最脆弱的一环

**站在一个实现者立场上**：`01` §7.10 说阈值"可配"，但没说配在哪。你把它配在渠道上，**那"同一渠道发不同货主、阈值要不要不同"？** 货主 A 的货小而轻，货主 B 的货大而重，**用同一个渠道同一个阈值，必然有一方是错的。**

**回应：这条打中了。** 阈值确实可能**需要「渠道 × 货主」两个维度**，而本文只给了渠道一个维度。**但我不能默认加维度**——`01` §7.10 没有这个意思，加它就是我编。**已并入 V7：若判为需按货主区分，§4.4 的接口要改成二元函数。**

### 反方 4｜两个实体、两个页面，对"九个词"的信息量是过度设计

**站在一个验收者立场上**：§6.2 里承运商 6 个字段**全是推的**，渠道 10 个字段里 **3 个是推的**。**近一半字段没有 `01` 依据。**

**回应：接受，且这正是 §0.3 存在的理由。** 我没有把推的字段混进"直给"里——**每一条都标了来源与强度**。**如果 Martin 的判法是"只留 `01` 直给的字段"，渠道表只剩 7 个字段、承运商表整体删除，本文照样成立——只是拆单阈值要另找宿主。** 这是有意的设计余量。

### 反方 5｜"渠道缺失进异常台账"会让异常量爆掉

**站在单据岗立场上**：货主在预报单上选渠道是靠人选的。**选错、漏选、选了停用渠道，每一种都进异常台账**——台账会被这条规则灌满，而 U28 明说"单据处理异常的原因 / 责任人 / 闭环时限还没定"。

**回应：接受前一半，不接受"因此不做"。** 异常量会在**渠道候选集没有过滤**时爆掉（货主看到全部渠道，当然会选错）。**这条恰好证明 V2 重要**——候选集必须收敛（按合同 / 按启用状态过滤），**候选集越收敛，异常越少**。而 U28 的待定状态**不是本文能解的**，如实挂在 §5.2。

### 反方 6（红队）｜干脆不做渠道主数据，让货主在每个预报单上填承运商与渠道名

**站在成本立场上**：这是最省的方案——**零主数据、零校验、零页面**。货主反正自己有快递账号。

**回应：这条在"客户是单一货主、渠道固定"时成立。** 本项目客户画像是 **20 仓 × 上百货主**（画像已定），**上百货主各填各的承运商名，一个仓一个月就是上千种写法**——汇总、对账、集包分组三件事全部失效。**渠道主数据的价值就在这里：花钱把"上千种写法"收敛成"几十条记录"。**

### 10.5 本文自身尚欠的缺口

- **渠道与「货主 × 仓」合同的绑定模型**——V2 若判为"按合同过滤"，**那个绑定关系挂在哪张表上，本文没给**。原因：它属"货主侧的商务表"（`README.md` §二.3 已注明六类全未建），本文越界。
- **多仓共用一条渠道的可能**——本文按"渠道挂单仓"建（`01` §9.1「仓级」）。**若客户要求"这条渠道在本集团 5 个仓都启用"，当前模型要建 5 条记录。** 我没有把它做成"渠道定义 + 仓启用关系"两张表，**因为 `01` 说"仓级"，我不擅自加一层**。如实挂着。
- **承运商档案与 `货主档案`（主体表）的关系**——承运商是法人，`货主档案` 也是主体表（`README.md` §二.1）。**理论上可复用，但会把"承运商"塞进语义为"货主"的表里**。本文选独立建表，**这条未与 Martin 确认**，属 V1 的延伸。
- **承运商下拉的候选范围**（反方 2 打中的）——"新建渠道时能选到哪些承运商"，本文没给交互细则。
