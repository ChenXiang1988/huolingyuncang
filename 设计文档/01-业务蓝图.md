**v12 修正清单：**

1. **（补缺口）新增 §6.5 出库单据链**：本文此前只写到"订单接收 → 交接承运商"，**预报、拆单、集包三件事没有位置**——而它们是货主与仓之间最常发生分歧的地方。本节给出链、三条时点与术语边界。
2. **（术语统一）**"到货预报"→**入库预报单**；出库起点单据＝**出库预报单**（货主端创建）。
3. **（补缺口）新增 §7.10 单据处理规则**：拆单两把刀（**不可混装** 硬约束在先、**金额/体积/重量阈值** 可配在后）、混装约束的三条口径、执行与兜底。
4. **（新增推论）2.5.5**：单据之间可以有引用关系，**引用不改单据身份**。**2.5.6**：拆单规则可配、由系统执行、执行不了进异常。
5. **（重大修正）§9.2「运输调度与路由」拆成三段**：渠道**主数据**由云仓维护（仓级）、**选择权在货主**（预报单给定）、**执行**在仓。**原文"承运商选择属货主或平台职责"过于笼统**，会把"云仓维护渠道主数据"读成越界。
6. **（新增推论）2.7.4 异常必须分两类**：作业异常 / 单据处理异常——后者的"原因、责任人、闭环"模型与前者的完全不同（§7.3）。
7. **（定值）库存实际扣减＝交接时**；货主**可拦截窗口＝集包完成之前**，之后只能走快递拦截 → 返库（复用 §6.3 退货主干）。§6.2 的"扣减时点必须明确"至此落为定值。
8. **（新增）反方 23**：「拆单规则可配 + 系统执行 + 异常兜底」把三个未验证的假设串成了一条通路。
9. **（新增未决）U24–U29**：混装是否上卷出库单 · 字段缺失算不算执行不了 · 拦截返库要不要质检 · 法规型清单来源 · 单据处理异常三要素 · 货主自带面单责任线。

**v10 修正清单：**

1. **（位置定死）套袋 / 贴标发生在出库流程，不在入库。** 依据（Martin 给的）：**同一件货品可能发 TEMU、SHEIN、Amazon，各平台包装与标签要求不同——加工方向由订单决定，而入库时不知道它要发哪儿。** 连带：场景 7、6.2 出库主干新增"出库加工"节点。

4. **（重写）2.10.7**：主形态定为"按单现场加工"，预先加工降为例外且**明确代价**（定向库存 = 消耗通用性）。

**v9 修正清单：**

1. **（修正）** 场景 10 原把"贴标"与"塑封 / 热缩"并列，归为"只消耗耗材、不改库存形态"的**外观加工**。**这个归类是错的**：塑封膜是**无信息**的耗材，**标签上有编码，编码来自外部**。贴标的本质是**标识赋权**，不是外观加工。二者必须分开。

5. **（新增）2.10.7**：套袋贴标的**发生时机有两种**（预先批量加工 / 按单现场加工），**两种在库存账上的表现不同**——与 v3 组套的"备货式 / 按单式"同构。

## 一、业态定义

三方云仓是**受托保管 + 代客作业**的生意。仓不拥有货，只提供场地、人力和作业能力。

### 1.1 钱从哪来

| 收入口 | 计价基础 | 特征 |
|---|---|---|
| 仓租 | 占用仓储资源 × 时间（库位/托盘/体积/天） | 接近过手，场地成本转嫁 |
| 操作费 | 动作 × 数量（收货件数、拣货行数、打包件数） | **真正的利润来源** |
| 增值服务费 | 贴标、换包装、组套、质检、二次加工 | 高毛利，高度非标 |

### 1.2 钱从哪出

| 成本口 | 内容 |
|---|---|
| 场地成本 | 租金、水电、折旧 |
| 人工成本 | 作业工时、班次、加班 |
| 差错成本 | 错发赔付、破损赔款、客诉、**货主流失** |

### 1.3 铁律：仓的利润 = 操作费 − 人工成本 − 差错成本

仓租基本是过手，仓真正在经营的是**单位动作的人工消耗**。

**产品含义：任何增加作业动作的功能，必须有明确的收益与之对冲。** 这就是为什么仓对系统的第一诉求永远是"少扫一次码、少走一步路"——不是懒，是利润结构决定的。

> **本铁律的适用范围已被自审限缩**，见 §10 反方 6：它不是硬性禁令，而是设计时的**默认质疑**，判据是差错的不可逆程度（2.9.3），不是动作数量。

### 1.4 产品边界：只做三方云仓（v2 新增，v5 定论）

Martin 于 2026-09-12 裁定：**卖给工厂的不划算，不如卖 MES，还是专心搞云仓。**

**边界就此锁死：**

| 类型 | 生意性质 | 是否纳入 |
|---|---|---|
| 电商仓、存储仓 | 三方云仓：**替别人保管** | **纳入**。这是产品的全部范围 |
| 工厂仓、原料仓、物料仓 | 工厂内部仓储：**管自己的料** | **不纳入**。这是 ERP 与制造执行系统的地盘 |

**裁定依据（推论，Martin 只给了结论，这是我替他补的理由，不是他的原话）：** 工厂内部仓储的价值不在"保管"，在"与生产计划咬合"——原料仓要算物料需求、要按工单齐套、要与工序在制品联动。这些能力属于制造执行系统，仓储软件做不过它，做出来也是半成品。**卖给工厂，卖的是一个残缺的 MES，不划算。**

**裁定带来的移出清单（v5 已执行）：**

- 场景「生产领用与退料」整节删除——它的出库由生产工单驱动，是工厂场景。
- §9.1「上游生产（生产工单 / 领料单）」删除。
- 角色「领料员」删除。
- 2.8.7 的仓功能类型收敛为云仓类。

**保留的部分（不要连带删错）：**

- **组套 / 塑封 / 随附仍然在内。** 它们发生在**电商仓**里，由货主的增值服务指令驱动，**不是生产工单驱动**。约束 10 因此完整保留。
- **跨仓调拨补货（存储仓 → 电商仓）仍然在内。** 两边都是云仓。

**产品不做自营（v7 定论，Martin 2026-09-12）：**

| 项 | 结论 |
|---|---|
| 仓自己买货来卖（自营经营） | **不做**。Martin 裁定：「肯定是不自营的，不会有这样的业态」（U2 关闭） |
| 仓在特定时点**被动**持有货权 | **必须有表达能力**。留置 / 弃件 / 赔付取得 / 代垫，见 **§3.5** |

> **这两行不是同一件事，混淆会出事故。** 不自营，指的是不建"自营价、自营成本、自营与代管的优先级"这一整套经营能力；被动持有货权，指的是货权因既有法律关系落到仓手上，它需要一个**所有权变更登记**，不需要任何经营功能。

## 二、行业公理与必然推论

### 2.1 约束层（10 条，推出产品内核）

#### 约束 1｜货权与保管权分离；库存是受托资产

**陈述**：库存在物理上共存于一仓，在权属上分属不同货主。仓对货只有保管责任，没有处置权。

**推论**：
- **2.1.1** 库存的原子单位不是"货品数量"，而是「货主 × 仓 × 货品 × 批次/效期 × 库位 × 库存状态」的多维记录。
- **2.1.2** 库存的每一次变化必须留下**不可篡改的变动流水**；任一时点的库存必须能从流水中还原（可回放对账）。
- **2.1.3** 库存状态必须可区分：可用、已占用（已分配未出）、冻结（盘点/质检/纠纷）、残次、待检、**在途（v2 新增）**。
- **2.1.4** 任何越权处置（报废他人的货、跨货主拆借、无单出库）必须在**模型层面不可表达**，而不是靠权限拦截。
- **2.1.5（v3 新增，v8 重写）** 库存对象**只有一类**——都是货主的财产，都走同一套「货主 × 仓 × 批次 × 库位」记录。但每个货品必须携带**两个正交的属性开关**：

  | 开关 | 含义 |
  |---|---|
  | **可售性** | 能否被订单直接拣出、发给消费者 |
  | **可作组件** | 能否出现在某个产出品的物料清单里、被消耗掉 |

  **这两个开关不互斥。** 四种组合都真实存在：

  |  | 可作组件 | 不可作组件 |
  |---|---|---|
  | **可售** | **套装件**：A、B 都能单独卖，也能组成套装 C 一起卖。**"可售商品被组合"是最常见的形态** | **普通商品** |
  | **不可售** | **组件物料**：包材、返利卡、赠品——只能被消耗，不能单独发货 | **纯耗材**：胶带、气泡膜、塑封膜——消耗在动作上，不产出成品 |

  > **v8 修正说明（Martin 指出，v3 的写法是错的）**：v3 按"用途"把库存分成两类，并给它们配了两条**互斥**的作业路径。**错在把用途当成了货品的固有属性。** 事实是——**同一个货品，在独立订单里是成品，在某个物料清单里是组件；可售商品被组合时，这两件事同时成立。** 互斥的前提根本不存在，所以不能按两类建模。
  >
  > 原版想防的两类事故（**把赠品当商品发出去**、**把随附的返利卡算成商品库存差异**）**依然要防**，但防法是**开关单独控制**，不是靠分类互斥。

- **2.1.6（v8 新增）** 因此，**「角色」不是货品的属性，是情境的属性**。推论：**物料清单里的组件可以是任何货品**——不存在"只有物料才能做组件"这种限制。02 的库存模型必须让"消耗来源"指向**任意 SKU**。

- **2.1.7（v8 新增）** **产出品的批次与效期必须能表达来源关系。** 组装消耗的多个组件可能来自不同批次，所以：

  - 产出品**生成新批次**，同时在产出记录里**登记消耗了哪些批次、各多少**（正反双向可追溯）。
  - **效期默认取所消耗组件中最早的那个**——套装里最先到期的那个限定了整体，这是行业惯例。
  - 但**必须可配置**（约束 6）：不管批次效期的仓 / 货品，产出品不生成批次。
  - **逆向组套（拆回）**：按原消耗记录回滚到原批次，还是回到新批次，同样是配置项。

- **2.1.8（v9 新增，标识层）** **一个货品可以有多个对外标识。** 货主有自己的货号，仓有内部编码，**每个销售渠道 / 平台有自己的一套编码**——同一个物理货品，在 TEMU、在其它平台、在不同店铺，是不同的 SKU。所以：

  - **"货品"是仓内部的身份，"标识"是对外交付的身份，两者必须分开建模。**
  - 一个货品下挂**一组对外标识**，每条标识携带**归属（哪个平台 / 渠道 / 店铺）+ 编码值 + 适用规则**。
  - **贴标这个作业的依据，全部来自这一层**——贴什么码、按谁的规则贴。**没有标识层，"贴标"在系统里没有数据可依，也校验不了贴错。**
  - **标识与"标签"不是一回事**：标签是**物料**（消耗、计成本，按 2.1.5 走库存），**标签上的码是标识**（数据、要校验、错了不可逆）。**混为一谈的结果是：系统只记得"用了几张标签纸"，不知道"贴的是哪个码"。**
  - **（v10 修正）关键在于：货品与标识是"多对多"，且用哪一个由订单决定，不由库存决定。** 同一件货，货主可能发 TEMU、可能发 SHEIN、可能发 Amazon——**货在库里的时候，它没有平台身份。**
    - **标识挂在订单 / 发货单上，不挂在库存上**（至少不是常态）。
    - 货品下挂的是**可用的标识映射表**（备查、校验用），**不是"已经贴好的标识"**。
    - 这条直接排除"把平台 SKU 作为库存主键一部分"的做法——**那样必然出现三笔库存，而货主入库时根本不知道这件货要去哪儿，拆了也建不出账。**

- **2.1.9（v9 新增，v10 修正，加工态）** **套袋这类动作，产出品与组件是同一个货品。** 组套是"组件 → 另一个货品"，套袋贴标是"**货品 A → 加了外包装的货品 A**"。2.10 的"组件 → 新产出品"框架必须能覆盖这种**自加工**（产出品的货品字段与组件相同）。

  - 它改变的是**销售单元形态**（裸装 → 可零售的袋装单元），**不只是"消耗了一个袋子"**。

  - **（v10 修正：位置定了——在出库，不在入库）** Martin 2026-09-12 指出：**同一件货品，货主可能要发 TEMU、可能发 SHEIN、也可能发 Amazon**，而**每个平台要求的包装形态与标签都不同**。**加工方向由订单决定，而订单什么时候来、发哪个平台，入库时不知道。** 推论有三层：

    1. **库存必须以"未定向的通用形态"持有。** 库里**不应该**有"TEMU 的货"与"SHEIN 的货"两笔账，**只有一件货**。
    2. **加工是出库流程的一个节点**（见场景 7 与 6.2），**不是库存的长期属性**。
    3. **如果出库时才加工，加工与发货几乎同时发生 → 库存账上不需要长期保留"加工态"这个状态。** 它在库里的存在时间极短。**这大幅简化了模型**——原 v9 设想的"可用量必须分状态统计"（反方 17），在默认形态下并不需要。

  - **唯一的例外是预先加工（定向备货）**：货主预判要发某平台，提前批量加工备着。这时库存里确实会出现**只能发某平台的"定向库存"**，反方 17 的问题才真正成立。**这是特例，不是默认**，见 2.10.7 与 U18。

#### 约束 2｜两套计价口径

**陈述**：仓租按"占用资源 × 时间"计，操作费按"动作 × 数量"计。两套口径，共用一套底层数据。

**推论**：
- **2.2.1** 计费引擎**长在作业数据上**，不是外挂的财务模块。计费是内核，不是附加功能。
- **2.2.2** 计费规则必须可配置到"每个货主一套"，且每一笔费用能追溯到由哪个作业动作产生（费用可解释）。
- **2.2.3** 必须支持库存快照能力：月末占仓量、日均占仓量、峰值占仓量。
- **2.2.4（v2 新增）** 仓租计价口径必须支持**容积维度**（体积 / 托盘位 / 层高归一化面积 / 原始底面积）。**同仓内层高不同的库位，按底面积计租会抹平差异**——层高 4 米和 8 米收一样的钱，仓自己就会亏。

#### 约束 3｜货主是客户，不是部门

**陈述**：货主会流失、会提要求、会比对、会砍价。是外部客户关系，不是内部协作关系。

**推论**：
- **2.3.1** 所有经营数据必须能按货主切片：库存、时效、差错、成本、利润。
- **2.3.2** 服务等级可按货主独立设定：时效承诺、异常处理时限、结算规则。
- **2.3.3** 必须有对货主可见的三本账：库存账、流转账、费用账。

#### 约束 4｜货主之间互为竞争对手，数据隔离是硬约束

**陈述**：同仓内 A 货主与 B 货主可能是同品类竞争对手。他们不接受被对方看见库存结构、销量节奏、货品清单。

**推论**：
- **2.4.1** 隔离必须进**模型底层**（数据归属层级），不能靠查询条件或权限配置来"过滤"。
- **2.4.2** 隔离的对象是**货主的对外可见面**，不是仓内作业。作业面必须打通（否则无法混波拣货），对外面必须隔绝。
- **2.4.3** 仓自身的经营数据（各货主的成本、利润）对任何货主均不可见。
- **2.4.4（v11 新增）隔离的边界是「数据」，不是「物理世界的连续画面」。**

  2.4.1–2.4.3 的隔离对象都是**可枚举、可按行归属**的数据。视频影像是**物理连续空间**的记录——同一条打包线上午服务 A、下午服务 B，镜头拍下来 A 与 B 的货在同一个画面里。

  **2.4.1 的"隔离必须进模型底层"在画面上无法成立**：画面不能按数据行过滤，要"隔离"只能裁剪——**而裁剪过的画面恰恰是证明力最弱的**，对方一句"你们给我看的是剪过的"就能反击整个记录体系。

  ⇒ **对影像，隔离对象必须换成「可见性与调取」**：采集不隔离、调取强制隔离、调取动作留痕。具体口径见 7.9.4。

  > **这不是对 2.4.1 的放松**，是把"隔离"这个词用在了它真正能生效的层面。**2.4.1 管的是数据可查询面，管不到物理世界里谁和谁的货同时出现在一个镜头里。**

#### 约束 5｜订单驱动且多来源

**陈述**：出库由订单驱动。订单来自电商平台、货主 ERP、货主自有系统、表格导入、人工录入。

**推论**：
- **2.5.1** 单据模型的**身份与状态机来源无关**：进系统后是同一种出库单，来源只是属性。
- **2.5.2** 但**作业语义来源相关**：平台单必须一包一面单，整托单允许合单发。来源特有的作业语义必须作为单据的**可扩展属性**保留，不能被归一化抹掉。
- **2.5.3** 上游对接必须可插拔，新增一个来源不改内核。
- **2.5.4** 上游不可靠是常态（漏推、重推、取消、改单），必须有对账与幂等机制。
- **2.5.5（v12 新增）单据之间可以有引用关系，引用不改单据身份。** 出库链是 **出库预报单 → 出库单 → 作业任务 → 集包单 → 交接单**（§6.5）。2.5.1 的"来源无关"讲的是**每一张单自身的身份**，不是说单据之间不能有层级。
- **2.5.6（v12 新增）拆单规则可配、由系统执行、执行不了进异常。** 判据两把刀：**不可混装（硬约束，先）**与**金额 / 体积 / 重量阈值（可配，后）**。口径见 §7.10。


#### 约束 6｜批次效期天生"可管可不管"

**陈述**：同仓内，化妆品货主要管批次效期，印刷品货主完全不管；甚至同一货主的不同货品规则也不同。

**推论**：
- **2.6.1（v2 改错）** "是否管批次 / 效期 / 序列号"必须是 **「仓 × 货品」级配置**。

  > v1 误写为"货品级"。**错在哪**：同一个货品在原料仓是整托进整托出、按生产工单领用；在电商仓是拆零拣货、一件一单。挂在货品上，就表达不了这个差异。**配置维度必须是「仓 × 货品」的交叉。**

- **2.6.2** 一旦启用，先进先出 / 先到期先出必须自动生效，不能靠人记。
- **2.6.3** 未启用的货品，这些维度必须能"空着走"，不能被强制填写。

#### 约束 7｜异常是常态，不是例外

**陈述**：少收、多收、破损、错发、拒收、库存差异，天天发生。

**推论**：
- **2.7.1** 异常必须有**独立台账与闭环处理流**：登记 → 定责 → 处理 → 闭环 → 影响结算。
- **2.7.2** 异常处理结果必须**回写库存与计费**，不能只停留在"备注"。
- **2.7.3** 收货环节必须支持"实收与应收不符"作为**正常流转**，而不是卡死流程。
- **2.7.4（v12 新增）异常必须分两类**：**作业异常**（人为动作产生的收发货差异）与**单据处理异常**（规则执行不了、配置与数据不匹配）。**两者的"原因、责任人、闭环"模型不同**，混在一本台账里，第二类会长期挂着没人认领。口径见 §7.3。


#### 约束 8｜仓是非标空间（v2 大幅扩充）

**陈述**：库位编码、区域划分、动线、拣货策略，每家仓不同，同一个仓改造后也不同。

**推论**：

- **2.8.1（新增）** 物理空间必须支持**层级结构**：仓 → 楼层 → 区域 → 货架/巷道 → 库位。层级可增减，不得写死。
- **2.8.2（新增，推翻 v1）** 库位不是一个编号，是一个**三维容器**：必须携带容纳能力（底面积 × 净高 × 承重）。

  > 层高不同的库位**不可等价**：同样底面积，层高 8 米的库位容量是层高 4 米的两倍。v1 把库位当"编号 + 容量口径"，不足以表达这件事。

- **2.8.3（新增）** 楼层带来三个硬约束：**承重上限、货运电梯（瓶颈资源）、垂直动线**。上架与拣货策略必须把它们当**约束条件**参与计算，不能当备注。
- **2.8.4** 库位体系必须可自定义：编码规则、层级、容量口径。
- **2.8.5** 拣货策略（按单、按波次、按区域、按路径）必须可配置且可切换。
- **2.8.6** 物理空间变化（加货架、改分区、改层高）不得要求改代码。
- **2.8.7（新增，v5 收敛）** 仓必须携带**功能类型**：**电商仓 / 存储仓**。不同类型的仓，**作业模式、单据类型、计费口径、时效要求全不同**。

  > v5 收敛：工厂仓 / 原料仓 / 物料仓三种类型随边界裁定移出（§1.4）。**类型字段本身保留**——云仓内部这两类确实不同：存储仓整托进出、周转慢、按占仓计租为主；电商仓拆零拣货、时效紧、按动作计费为主。
- **2.8.8（新增，本节最关键）** 因此**作业规则挂在「仓 × 货品」的交叉上**，既不挂货品，也不挂系统。

#### 约束 9｜精度是有成本的

**陈述**：系统每要求一次确认动作，都转化为仓的人工成本。

**推论**：
- **2.9.1** 精度必须**可调**：同一套系统要能跑"只管件数"和"管到批次库位"两种强度。
- **2.9.2** 每增加一道强制校验，必须能说清它挡住的是哪类错误，以及该错误的历史成本是否高于校验成本。
- **2.9.3 裁决规则（本节最关键）**：校验强度按**差错后果的不可逆程度**分档，不按货品价值分档。
  - 不可逆错误（发错货主、发错地址、错发货品）→ 强制校验
  - 可逆错误（库位小差异、数量小偏差）→ 允许后补 + 事后盘点纠正

  > 这是本蓝图对"账要准"与"别加动作"这对矛盾的**唯一裁决方式**。没有它，约束 1 和约束 9 的推论会互相打架。

#### 约束 10｜仓内会发生改变货物形态的作业（v3 新增）

**陈述**：货主会要求仓把组件与客供物料组装成新形态后再发出——组套装、放返利卡、塑封、换包装、**套袋、贴标**。**组件可以是可售商品（A + B → 套装 C），也可以是客供物料（包材、返利卡），二者在规则上无差别**（2.1.6）。这**不是"搬运"，是"消耗 + 产出"**。

**v9 补充（Martin 指出）**：仓内加工**不止"改变货物形态"一种**，而且极易被归错——**给货品贴上外部标识**（如平台分配的 SKU 标签）。它看起来像"外观加工"，**但它改变的不是货品的外观，是货品对外的可识别性**：贴错了，货到了平台仓扫不出来，**整批拒收**。所以约束 10 的范围应表述为"**仓内会发生改变货物形态或对外标识的作业**"。

**v10 补充（Martin 纠正）**：这类作业**主要发生在出库环节，不在入库**。因为**加工方向由订单决定**——同一件货可能发 TEMU、SHEIN、Amazon，入库时不知道它要发哪儿（详见 2.1.9）。**这不是位置细节，它决定了库存以什么形态存在。**

**推论**：

- **2.10.1** 必须支持**物料清单**：一个产出品由哪些组件 × 数量构成。**组件来源不限——可售商品与客供物料地位相同**（2.1.6）。
- **2.10.2** 作业必须**同时记账**：组件与物料**消耗**、产出品**入库**。只记一边，账就断了。
- **2.10.3** 必须能核算并登记**损耗**——塑封膜会废、卡片会损、包装会破。

  > 货主一定会问："我给你 3000 个 A、3000 个 B，你做出来 2900 套，那 100 套的组件去哪了？"
  > **损耗对账是组套场景的核心能力，不是附加功能。** 没有它，货主与仓之间必然扯皮。

- **2.10.4（v8 修正）** 组装**必须能预留组件**，组件不足不得开工——否则会出现"领到一半发现不够"。

  > **但当组件本身是可售商品时，"预留"就等于拿能卖钱的货去占住。** 同一批 A 既可能被组装消耗，也可能被独立订单拣走。**谁优先不由技术规则单方面决定**——这是业态问题，见 **U17**。技术侧只守一条：**争用必须可见、可配、可留痕，不允许系统偷偷把已预留的货挪走。**
- **2.10.5 范围红线**：**只做"物料消耗与产出记账"，不做生产管理**（工单排产、工序流转、工时、在制品）。

  > 这条红线是防止产品膨胀成生产管理系统。判据：电商仓的组装是**分钟级的动作**，不是天级的生产周期；一旦引入工单排产与工时，就与约束 9（精度有成本）直接冲突。
  > 反过来说——**工厂侧的生产领用已随边界裁定整体移出产品范围**（§1.4），所以本约束的适用范围只剩云仓内的组套 / 塑封 / 随附 / 套袋 / 贴标。

- **2.10.6（v9 新增）平台合规规则是一个独立的规则来源。** 举例：某个货主的订单是 **TEMU 备货单**，那这批货至少需要**套袋 + 贴 SKU 标签**两个仓内动作。这两个动作的要求**不是货主定的，也不是仓定的，是平台定的**。

  - 这类规则的特征：**来源在外部（平台）、强制（不遵守就拒收）、带版本（不同时间下的单适用不同版本）、会变（平台改规则，仓与货主都得跟）。**
  - 它与 2.5（订单多来源）不是一回事。**2.5 讲的是单据的身份与作业语义，这里讲的是外部的合规约束**——比作业语义更外一层。
  - **能力边界（必须写死，否则就是空头支票）**：产品**管**"规则可配置、可带版本、变更留痕、历史单据仍可解释"；产品**不管**"自动跟踪平台规则变化"。**平台改规则的输入永远靠人。** 理由见反方 18。
  - **（v10 补充）触发点必须说清：这类规则由订单带来，不由入库带来。** 同一件货，TEMU 单要求的加工与 SHEIN 单要求的加工**可能完全不同**；同一个平台的不同店铺、不同国家站点也可能不同。**这正是"标识层"（2.1.8）必须存在的原因**——没有它，系统无法回答"这一单要贴哪个码、按哪一版规则"。

- **2.10.7（v9 新增，v10 重写）套袋贴标的时机有两种，主次必须说清。**

  | 时机 | 做法 | 库存账上的表现 | 定位 |
  |---|---|---|---|
  | **按单现场加工** | 订单确定后，拣出来、**打包之前**现场套袋贴标 | 库存**不出现加工态**，只消耗袋与标签 | **默认形态**（v10 定）。理由见 2.1.9：加工方向由订单决定 |
  | **预先加工** | 预判要发某平台，提前批量套袋贴标备着 | 库存里**出现"定向库存"**——只能发该平台、不能发别的渠道 | **例外，且有代价**。见反方 17、20，与 U18 |

  > 这与 v3 组套的"备货式 / 按单式"是**同一个结构**。
  > **但有一处关键差异**：组套的备货式是常态（**套装本来就是独立的可售商品**）；**套袋贴标的预先加工会产生"定向库存"，而定向库存是对通用性的一次消耗**——平台单没来、改规则、或量估错了，这批货就砸在手里。**所以默认档必须是按单现场加工，预先加工只能是货主明确要求并承担风险时的选项。**

### 2.2 目标层（3 条，进入度量与验收）

| 编号 | 目标 | 口径方向 |
|---|---|---|
| 目标 A | **库存准确率** | 账实一致。信任货币。 |
| 目标 B | **时效达成率** | 收货上架时效、出库及时率、异常响应时效 |
| 目标 C | **单位操作成本** | 每单 / 每件 / 每行的作业成本 |

**约束层是"必须遵守"，目标层是"必须改善"。**

### 2.3 推论与目标的挂接表

| 推论 | 服务目标 |
|---|---|
| 2.1.1 – 2.1.4 | A、C |
| 2.2.1 – 2.2.4 | C |
| 2.3.1 – 2.3.3 | A、B |
| 2.4.1 – 2.4.3 | A（信任基础：信任不只是准确，还有不外泄） |
| 2.5.1 – 2.5.4 | B |
| 2.6.1 – 2.6.3 | A |
| 2.7.1 – 2.7.3 | A、C |
| 2.8.1 – 2.8.8 | C、A |
| 2.9.1 – 2.9.3 | C |
| 2.10.1 – 2.10.5 | A、C（组套做错 = 对不上账；损耗失控 = 成本失控） |

### 2.4 为什么做这些结构性调整

- **移出"人枪协作/容错设计"**：它说的是"该怎么设计"，不是"逃不掉的约束"。公理里混进设计原则，就是自证循环——先假定容错设计，再用它推出容错设计。
- **移出"准确率是信任货币"**：它是评价标准，不是约束。混进公理表，度量就会被公理绑架。
- **新增约束 4（数据隔离）**：原版只有"货主是客户"，讲的是**服务关系**，漏了**排斥关系**。
- **新增约束 9（精度有成本）**：原版漏掉，直接导致"系统越严格越好"的错误直觉。
- **扩充约束 8（v2）**：原版把"仓"当成一个扁平的空间。"多类型仓 + 楼层 + 层高"证明仓内部本身就是异质的，必须分层建模。

## 三、主体与货权

### 3.1 三个主体

| 主体 | 是什么 | 对货的关系 |
|---|---|---|
| **仓（作业方）** | 场地 + 人力 + 系统，提供保管与作业 | 有**保管责任**，无处置权；**被动取得货权的情形除外**（§3.5） |
| **货主（委托方）** | 货的所有权人 | 有**处置权** |
| **货** | 被保管对象 | 身份 = 货主 + 仓 + 货品 + 批次 + 状态 |

### 3.2 货权三层

- **所有权**：归货主。仓不可处置——**除被动取得货权的情形**（§3.5），那是法律关系的结果，不是经营行为。
- **占有权**：物理上在仓里，仓实际控制。
- **处置权**：只有货主能授权，且授权必须**单据化、可追溯**。

### 3.3 主体位置的分离

**关键推论**：货主角色与货主主体会分离。典型场景——货主是一家电商代运营公司，实际货物属于品牌方；结算对象与货物归属不是同一个。

所以主体模型必须能表达**四个可分离的位置**：

| 位置 | 含义 |
|---|---|
| 货物归属方 | 货是谁的 |
| 下单方 | 谁发的出库指令 |
| 结算方 | 谁付仓租和操作费 |
| 看数方 | 谁能看这批货的数据 |

四者可以是同一个主体，也可以是四个不同主体。**把它们设计成一个字段，代运营类客户就接不了。**

### 3.4 货主 × 仓 的二维（v2 新增）

**一个货主不会在所有仓里都有货。** 现实形态是：

- 货主把一个电商仓和若干存储仓都租下来 → 合同、结算、服务等级按「货主 × 仓」分别成立
- 货主只在电商仓有货，存储仓完全没他的事 → 他看不见存储仓的任何数据
- 同一个货品在货主名下的不同仓里，作业规则不同（见 2.8.8）

**推论：**

- **3.4.1** 合同、计费规则、服务等级承诺的**归属单位是「货主 × 仓」**，不是货主。
- **3.4.2** 数据可见性的**边界也是「货主 × 仓」**：货主只能看见自己有货或有合同的仓。
- **3.4.3** 库存、容量的统计与配额，单位同样是「货主 × 仓」——一个货主在 A 仓满了，不代表 B 仓也被占。
- **3.4.4** 因此，**"货主"不是模型里最高的一层，"仓"也不是**。二者是交叉的两维，缺一不可。

### 3.5 货权的被动转移（v7 新增）

**背景**：Martin 于 2026-09-12 裁定**本产品不做自营**（U2 关闭）。

**但"不自营"不等于"仓永远不会持有货权"。** 这两件事常被混成一件，一旦混了，下面四类场景会在系统里无处安放：

| 情形 | 货权怎么变 | 时间特征 |
|---|---|---|
| **留置** | 货主欠费不结清，仓依法对货物行使留置权 | 处置前货在仓手，**货主可能失联** |
| **弃件** | 退货件、无主货长期无人认领；货主明确弃权或超期视同弃权 | 拖得很久，**数月量级** |
| **赔付取得** | 破损 / 丢失已赔偿，残值或整批货归仓 | 赔付完成即转移 |
| **代垫代购** | 仓替货主采购包材并垫付，实物已混入货主的物料库存 | 高频、小额、**易被忽略** |

**这四类都不是"经营"，都是法律关系的结果。**

**推论：**

- **3.5.1** 模型必须支持**在既有货物上变更所有权归属**（货主 → 仓、仓 → 货主、仓 → 第三方），且与库存变动一样**留不可篡改流水**（2.1.2）。
- **3.5.2** 但**不为此建"自营经营"能力**：不设自营价、不做自营成本核算、不设自营与代管的优先级（U10 已关闭）。
- **3.5.3** 仓持有货权期间，这批货**按普通库存对待**——一样占库位、一样产生费用、数据隔离照旧，差别仅在**归属方字段指向仓自己**。
- **3.5.4** 这类货的**处置（售出 / 报废）必须走独立的处置单据**，**不得直接出库**——它没有"货主的出库指令"可作为依据。这是 2.1.4（越权处置在模型层面不可表达）的直接应用。

**红队（对立做法）**：这类货一律不进系统，走线下处置台账。**否掉。** 留置与弃件的时间跨度常达数月，线下台账必然与系统库存脱节——**系统里这批货还挂着，实物早已处置**，直接违反 2.1.2 的可回放对账。

## 四、角色与职责

### 4.1 仓内角色

| 角色 | 职责 |
|---|---|
| 仓负责人 | 经营结果、货主对接、异常定责 |
| 收货员 | 卸货、清点、验收、实收登记、异常登记 |
| 上架员 | 库位分配与上架确认 |
| 拣货员 | 按任务取货 |
| 复核打包员 | 核对、装箱、称重、贴面单 |
| 盘点员 | 定期盘点与循环盘点 |
| 组装员 | 组套、组装、塑封、随附（v3 新增） |
| 客服跟单 | 对接货主、异常跟进 |
| 财务结算 | 计费、对账、开票 |
| 系统管理员 | 货主开通、规则配置、权限 |

> v2 补充：多仓场景下，角色还要能**按仓限定**——同一个人可以在电商仓有拣货权限、在存储仓没有。所以角色与权限的绑定单位同样是「人 × 仓」。

### 4.2 货主侧角色

| 角色 | 职责 |
|---|---|
| 货主操作员 | 下单、查库存、查物流 |
| 货主财务 | 对账、结算确认 |
| 货主管理者 | 看经营与时效数据 |

### 4.3 权限模型的硬约束

**仓内角色是按"动作"切的，不是按"部门"切的。**

同一个人一天里可能既收货又上架。所以权限必须**按动作授权**，不是按岗位授权——否则小仓根本配不出权限（人不够，岗位套不上）。这条直接来自"仓是非标空间"与"精度有成本"两条约束。v2 起再加一层：**动作授权要与「仓」绑定**。

## 五、场景全集

13 个场景。每个场景给出：触发、参与角色、关键节点、异常分支、服务目标。

### 场景 1｜货主与货品准入
- **触发**：新货主签约 / 新货品上架
- **角色**：系统管理员、货主
- **节点**：货主开通 → **按仓设定**服务等级与结算规则 → 货品建档 → **「仓 × 货品」规则设定**（批次/效期/序列号/包装/作业模式）
- **异常**：货品信息不全（无条码、无规格）→ 建档时的兜底规则
- **目标**：A

### 场景 2｜收货入库（v2 分型）
- **触发**：**入库预报单** / 实际到货
- **角色**：收货员
- **入库类型（决定单据与作业动作）**：

| 入库类型 | 典型仓 | 特征 |
|---|---|---|
| 采购到货入库 | 存储仓 | 对采购单，批次/效期强。货主自己采购的货直发仓 |
| 调拨入库 | 电商仓、存储仓 | 来源是另一仓，需对调拨单 |
| 退货入库 | 电商仓 | 需质检判定，良品/残次分流 |
| 补货入库 | 电商仓 | 从存储仓补来，通常整托 |
| 无预报到货 | 任意 | 无单到货，必须走异常通道 |
| **客供物料入库（v3 新增）** | 电商仓 | 货主直接寄来的包材、返利卡、赠品。**通常无采购单、无条码、不定期、量小**。必须先建档再入库，**入库结果必须回传货主确认**——货主会关心"我寄的 500 张卡到了几张"。**数量以仓实收为准、须存证，差额必须登记并结案（v6，见 7.8）** |

- **节点**：卸货 → 清点 → 验收 → **实收登记（影像锚点，见 7.9）** → 差异登记
- **异常分支**：少收 / 多收 / 破损 / 无预报到货 / 货不对版 / 拒收 / **客供物料无标识、与既有物料重名、货主未提前通知**
- **目标**：B、A

### 场景 3｜上架
- **触发**：收货完成
- **角色**：上架员
- **节点**：库位分配（系统建议，需考虑**容积、承重、楼层、动线**）→ 上架确认
- **异常**：库位不足、库位被占、混放冲突、**超承重、电梯运力不足**
- **目标**：C

### 场景 4｜库存管理
- **触发**：日常
- **角色**：仓负责人、系统管理员
- **节点**：库存查询 → 库存调整（带原因）→ 冻结/解冻 → 仓内移库
- **异常**：无单调整、跨货主移库（必须不可表达）
- **目标**：A

### 场景 5｜盘点
- **触发**：周期计划 / 动碰盘 / 专项
- **角色**：盘点员、仓负责人
- **节点**：盘点计划 → 盘点任务 → 实盘录入 → 差异比对 → 差异处理（含定责）→ 库存与计费回写
- **异常**：盘盈、盘亏、盘点期间有作业
- **目标**：A

### 场景 6｜波次与拣货
- **触发**：订单接收
- **角色**：拣货员
- **节点**：订单接收 → 波次规划（考虑**楼层与路径**）→ 拣货任务下发 → 拣货确认 → 缺货登记
- **异常**：缺货、库位空、库存被占用、订单取消（拣货中）
- **目标**：B、C

### 场景 7｜复核与打包（v10 扩充：纳入出库加工）
- **触发**：拣货完成
- **角色**：复核打包员、作业员
- **节点**：复核（品/量/货主）→ **出库加工（按订单定向：套袋 / 贴平台 SKU 标签 / 换包装）** → **装箱（影像锚点）** → 称重 → **贴面单（影像锚点，见 7.9）**
- **异常**：复核不符、超重、面单异常、**加工物料（袋 / 标签）不足**、**贴错标（码不对 / 贴错面 / 贴错货）**、**平台规则版本与单据不符**
- **目标**：A（不可逆错误的最后一道闸）、B
- **v10 说明（Martin 指出）**：套袋 / 贴标**发生在出库流程，不在入库**。理由：**同一件货品，货主可能发 TEMU、可能发 SHEIN、可能发 Amazon**，各平台包装与标签要求不同，**货在库里的时候没有平台身份**（2.1.9）。
  - **因此加工是"订单维度"的动作，不是"货品维度"的动作。** 同一批货按不同订单被加工成不同形态，**是常规，不是异常**。
  - **必须与"贴面单"分开**：面单是**物流单**（承运商给的，贴包裹外，属约束 5 的作业语义）；平台 SKU 标签是**商品标**（平台给的，贴商品本身，属 2.1.8 的标识层）。**一个是包裹的身份，一个是商品的身份，位置与依据都不同。**
  - **贴标必须在装箱前完成**，且按 2.9.3 属于**不可逆错误**（货到平台仓扫不出 = 整批拒收）→ **强制校验**：贴前扫货品、贴后扫标签、系统比对。

### 场景 8｜出库交接
- **触发**：打包完成
- **角色**：仓负责人、承运商
- **节点**：交接给承运商 → 出库确认 → 轨迹跟踪 → 签收
- **异常**：漏交、晚交、承运商拒收、丢件
- **目标**：B

### 场景 9｜退货
- **触发**：货主退货指令 / 消费者退回
- **角色**：收货员、客服跟单
- **节点**：退货接收 → 质检 → 判定（良品回库 / 残次 / 报废）→ 结果回传货主
- **异常**：无主退货、超期退货、破损严重、货已停售
- **目标**：A、C

### 场景 10｜库内增值作业（v3 大幅细化，v10 划界）

- **触发**：货主增值服务指令
- **角色**：作业员、组装员
- **v10 划界**：本场景管**库内**加工（组套、塑封、随附，以及**预先**套袋贴标）。**"按单现场套袋贴标"不在这里，在场景 7 的出库流程中**——它的加工方向由订单决定（2.1.9），它是**订单履约的一个节点**，不是库存作业。
- **v3 关键区分**：下面几件事**看起来都是"加工"，作业路径完全不同，不能合并成一个功能**：

| 形态 | 做什么 | 是否改变库存形态 | 发生时机 |
|---|---|---|---|
| **随附** | 拣完货后往包裹里加塞物料（返利卡、赠品） | **否**。只消耗物料，商品库存不变 | 打包环节 |
| **组套** | 组件 + 物料 → 组装成新的产出品。**组件可以是可售商品**（A + B → 套装 C），不限于物料（2.1.6） | **是**。组件消耗、新产出品入库 | 预先做（备货式）**或**接到订单后现场做（按单式） |
| **塑封** | 对成品做塑封 / 热缩等**外观**加工 | **否**。只消耗耗材（塑封膜等**无信息**的耗材） | 组装之后，或对原有商品单独做 |
| **套袋**（v9 新增） | 给裸装货品加外包装袋，使其成为可零售的销售单元 | **否**（按 2.1.9 是**加工态变化**，不是数量变化） | **主要在出库环节**（场景 7）；预先加工是特例，见 2.10.7 |
| **标识赋权**（v9 新增，即"贴标"） | 给货品贴上**外部标识**（如平台分配的 SKU 标签） | **否**。消耗标签物料，**但改变的是货品的对外可识别性**（2.1.8） | **出库环节，装箱前**（场景 7），理由见 2.1.9 |

- **组套的两种作业模式，产品必须都支持**：

  | 模式 | 做法 | 库存账上的表现 |
  |---|---|---|
  | **备货式** | 先批量组装成产出品入库，之后按普通商品拣货发货 | 库存里**多出一个产出品**，组件减少 |
  | **按单式** | 接到订单后现场组装 | 库存里**不出现产出品**，只有组件与物料被消耗 |

  > **这两种模式在库存账上的表现完全不同。** 只支持一种，另一个场景就得靠人手工糊账。

- **节点**：指令接收 → 检查组件与物料是否齐备 → **预留组件** → 领料 → 作业 → 产出登记（含损耗）→ 结果回传货主
- **异常**：组件不足、物料不足、**损耗超标**、指令与实物不符、**组装完卖不掉要拆回（逆向组套）**、**贴错标（码不对 / 贴错面 / 贴错货）**、**平台规则版本与单据不符**
- **v9 关键区分**：**贴错标属于"不可逆错误"**——货到了平台仓扫不出来就是整批拒收，退回来的成本远高于贴标动作本身。按 2.9.3 的分档规则，它**必须强制校验**（贴之前扫货品、贴之后扫标签、系统比对），**不能归入"允许后补"的低档**。这条同时说明：**"标识赋权"和"外观加工"不能按同一档的精度处理。**
- **目标**：C（高毛利，成本核算必须独立）、A

### 场景 11｜仓内移库与仓间调拨补货（v2 新增，v5 重编号）
- **触发**：库位优化 / 货主指令 / **补货需求（存储仓 → 电商仓）**
- **角色**：仓负责人
- **节点**：调拨单 → 出库确认 → **在途状态** → 入库确认 → 两边库存同时更新
- **异常**：在途丢失、调拨不核对、跨货主（必须不可表达）
- **目标**：A、C
- **v2 说明**：v1 把跨仓调拨当边缘场景。**在"存储仓 + 电商仓"的形态下，它是主干**——存储仓的货要持续补到电商仓去卖。所以它必须支持**在途库存**这一种独立库存状态，且必须能按调拨单双向对账。

### 场景 12｜计费与结算
- **触发**：结算周期到 / 货主查询
- **角色**：财务结算、货主财务
- **节点**：费用生成 → 对账 → 确认 → 结算 → 出账
- **异常**：费用争议、计费规则变更追溯、异常费用冲减
- **目标**：C
- **v2 说明**：计费的单位是「货主 × 仓」，不是货主。

### 场景 13｜货主退仓与清货
- **触发**：货主终止合作 / 转仓
- **角色**：仓负责人、财务结算、货主
- **节点**：退仓申请 → 库存清点 → 费用结清 → 货物清退 → 责任终止 → 数据归档
- **异常**：库存差异定责、尾货滞留、欠费货物处置、数据保留期
- **目标**：A、C

## 六、主干流程

### 6.1 入库主干

```
**入库预报单** → 卸货 → 清点 → 验收 → ┬─ 一致 → 实收登记 → 库位分配 → 上架确认 → 库存可用
                                  └─ 不一致 → 差异登记 → 异常台账 → 定责 → 影响结算
```

**判定点**：实收与应收是否一致 / 是否启用了批次效期（启用则必须采集批次）/ 是否需要质检 / **属于哪种入库类型**。

### 6.2 出库主干

```
出库预报单（货主端）→ 〔云仓端：系统校验放行 / 异常转人审〕→ 出库单 ×N
   → 波次规划 → 拣货任务 → 拣货确认
   → 复核 → 出库加工（按订单定向：套袋 / 贴平台标签）→ 装箱称重 → 面单
   → 集包（按渠道）→ 交接承运商 → 出库确认 → 库存扣减 → 计费触发
```

**判定点**：库存是否足够（不足则缺货分支）/ 是否需要批次指定 / **本单是否需要出库加工（按平台规则）——v10 新增**。

> **v12 修订两处**：① 起点由"订单接收"改为**出库预报单**——订单来源（平台 / ERP / 表格 / 人工）是预报单的**输入**，不是出库主干的起点；② **"是否需要合单或拆单"从本判定点移出**——拆单发生在**云仓端校验放行时**（§7.10），单仓端只接收**已拆好的出库单**。判定点的上移不等于决策主体的上移，此处按"在这一步发生"读。

**注意（v12 落为定值）**：库存扣减的时点——**拣货时预占、交接时实际扣减**。原"必须明确"至此关闭。**货主可拦截的右边界是「集包完成」，之后只能走快递拦截 → 返库**（§6.5）。

### 6.3 退货主干

```
退货接收 → 质检 → 判定 ┬─ 良品 → 回库上架
                        ├─ 残次 → 残次库位
                        └─ 报废 → 报废登记 → 回传货主确认
```

### 6.4 仓间调拨补货主干（v2 新增）

```
补货需求 → 调拨单 → 调出仓出库确认 → 在途库存 → 调入仓入库确认 → 两边库存同步更新
```

**判定点**：在途期间货权归谁 / 在途丢失如何定责 / 调拨单与实物是否核对。

**为什么把它列为独立主干**：存储仓补电商仓是这套业务的日常动作，不是例外。**"在途"是一种必须被建模的库存状态**，否则两边都对不上账。这一条与 v1 反方 3 是同一类问题——**别把必然存在的中间状态当成异常**。

---

### 6.5 出库单据链（v12 新增）

**为什么单列一节**：v11 之前本文的出库只写到"订单接收 → 交接承运商"，**预报、拆单、集包这三件事在本文没有位置**——而它们恰好是货主与仓之间最常发生分歧的地方（一张预报为什么变成两张出库单、为什么多算一次操作费）。

```
出库预报单（货主端创建，只指定 1 个仓）
        │
        ├─〔云仓端：系统校验放行 ／ 异常转人审〕
        ▼
出库单 ×N ──→ 作业任务（拣货 / 贴标 / 复核 —— 顺序由订单类型编排）
        └──→ 包裹（箱；1 箱 : 1 面单）──→ 集包单（按渠道，多张出库单 → 1 张集包单）
                                          └──→ 交接单（交接 → 库存扣减 → 计费触发）
```

**三条时点（必须一起读）**：

| 节点 | 含义 |
|---|---|
| **预报单放行前** | 货主可**撤回** |
| **集包完成** | 货主**可拦截**的右边界；之后仓内拦不住，只能走**快递拦截 → 返库**（复用 §6.3 退货主干：接收 → 质检 → 判定 → 良品回库上架） |
| **交接** | **库存实际扣减点**（拣货时只预占） |

**术语边界（防混淆）**：**拆单** ＝ 1 张预报单 → N 张出库单；**分箱** ＝ 1 张出库单 → N 箱 / 面单；**集包** ＝ N 张出库单的包裹合成一个交接批次。**本版不使用"合单"一词**——它与 2.5.2 的"整托单允许合单发"是两件事（前者是作业级合并，后者是订单级合并），同词两义必生歧义。**2.5.2 原文保持不动。**

> **"合单"一词的取舍属用词裁定，Martin 尚未直接表态**；本文取用「拆单 / 分箱 / 集包」三词，若您要求保留"合单"，改回不影响本节结构。

**状态机（推论，上游未给）**：

```
出库预报单：草稿 → 已提交 → 校验中 → 已放行 / 已驳回 → 执行中 → 已完成
                              ↘ 已撤回（放行前，货主发起）
出库单：待拣货 → 拣货中 → 待加工 → 待复核 → 待集包 → 已集包 → 待交接 → 已交接（扣减）
                                                     ↘ 已拦截（集包前，仓内操作）
```

**责任端**：预报单**由货主端创建** · 校验放行与异常人审**在云仓端** · 出库单以下**全在单仓端**。**选仓由货主端决定，云仓不参与选仓建议**（Martin 2026-09-26 裁定）——因此**本文不存在"寻源拆单"**（行业里拆单的第一大原因是跨仓分配，本项目由货主指定仓而天然排除）。

## 七、规则

### 7.1 权限规则
按**动作**授权，且与**仓**绑定。动作清单的精度是未决项（U7）。

### 7.2 时效规则
每条时效承诺按「货主 × 仓」可配，且必须能按「货主 × 仓」统计达成率。承诺不能只写在合同里，必须进入系统并被度量。

### 7.3 异常闭环规则
四要素缺一不可：**登记必填原因、处理必有责任人、闭环必有时限、结果必须回写库存与计费**。

**v12 新增：异常分两类（2.7.4），共用一本台账但必须分类**（Martin 2026-09-26 裁定）：

| 类 | 例 | 特征 |
|---|---|---|
| **作业异常** | 少收 / 多收 / 破损 / 拒收 / 货不对版 | 人为动作产生；责任人＝现场；**多数要回写库存与计费** |
| **单据处理异常**（v12 新增） | 拆单规则执行不了 / 增值能力未启用 / 渠道缺失 / 规则引用的字段缺失 | **规则与数据不匹配**，不是人为差错；责任人＝云仓端单据岗；**多数只改单据状态、不回写库存**（货还没动） |

> **第二类的"原因 / 责任人 / 闭环时限"如何定义，尚未定（U28）**——上面那套四要素是为第一类设计的，直接套用会让系统抛出的异常无人认领。
> **云仓端的单据运行异常视图只展示异常、不展示正常件**（Martin 2026-09-26 裁定）；两端的异常入口（货主端 / 单仓端 / 云仓端）的可见与可操作差异，尚未写。


### 7.4 计费规则口径
- 两套口径并存：占仓计费（含容积维度）、动作计费
- 规则可版本化，变更不得追溯修改已出账的历史
- 每笔费用可下钻到来源作业记录

### 7.5 校验强度分档规则
按**差错后果不可逆程度**分档（见 2.9.3）：
- 不可逆 → 强制校验，不通过不放行
- 可逆 → 允许后补，靠盘点与复核纠正

### 7.6 作业规则配置规则（v2 新增）
作业规则（批次/效期/序列号/包装/拣货策略/校验强度）的配置单位是 **「仓 × 货品」**，不是货品、不是仓、也不是系统。

### 7.7 物料清单与消耗产出规则（v3 新增）

- 产出品必须有**物料清单**：列出组件与物料及其数量。**组件可以是任意货品，包括可售商品**（2.1.6）——"拿能单独卖的商品去组装"是常规形态，不是例外。
- **消耗与产出同笔记账**，不允许只记一边。
- **损耗必须登记原因与数量**，并按「货主 × 仓 × 产出品」统计。
- 组件不足**不得开工**；开工前必须预留组件。
- **逆向组套（拆回）必须支持**，且同样要记损耗。
- **容量层面必须全，界面层面必须收**：模型支持全部组套能力，但**界面与流程按「仓 × 货品」开关**——未启用组套的仓看不到这些操作。理由见反方 7 的红队回应。
- **范围红线**：不做工单排产、工序流转、工时、在制品。
- **（v9 新增）套袋 / 贴标走同一套记账框架，但有三个要点**：① **产出品的货品字段与组件相同**（自加工，2.1.9）；② **标签物料与标签上的标识必须分开记**（2.1.8）——物料记消耗，标识记赋权；③ **贴标必须在出货前完成且有校验**，贴错标按不可逆错误处理（场景 10）。

### 7.8 客供物料的入库责任口径（v6 新增）

**前置口径（合同层面，不入系统）**：客供物料的数量**以仓入库实收为准**；货主随寄**须附装箱单**；无装箱单的，**以实收为终**。

**系统层面只需且必须做三件事**：

1. **入库存证**：数量必录，并留可追溯的佐证（影像 / 重量 / 封条，具体档位按 7.5 的分档规则确定）。证据与入库单绑定，不可单独删除。**其中「影像」一词的完整口径见 7.9（v11 定义）。**
2. **当场回传货主确认**：实收数入库后即刻对货主可见；货主可确认或申辩，申辩走异常台账。
3. **差额进异常台账**：少收 / 多收必须登记原因、责任人、时限，并回写库存与计费（7.3）。

**系统明确不做的**：**不承诺"验证货主实际寄出多少"**——该信息不在仓手里，任何号称能验证的设计都是假的。

**留证的硬约束**：留证动作必须**挂在既有的入库扫码动作上**，不得新增独立环节；留证强度按差错后果不可逆程度与货值分档，**不得对低值可补物料强制全量留证**（理由见反方 13）。

### 7.9 作业影像留证口径（v11 新增）

**本文此前只有 §7.8 一处提到"影像"，把它与"重量 / 封条"并列，当作一个未定义的档位。本节把这个词具体化，并把范围从客供物料入库扩展到收货与打包两个环节。**

#### 一、为什么只做这两个环节

| 环节 | 为什么必须留证 |
|---|---|
| **收货** | **实收数是一切争议的起点。** 7.8 已定"以实收为终"，而单方数字在纠纷里站不住（反方 10）——**影像就是这条口径的对价** |
| **打包** | **不可逆错误的最后一道闸**（场景 7 目标 A）。货一旦出库，错发无法追回 |

**其余环节（上架、拣货、盘点）的差错按 2.9.3 属"可逆错误"，走"后补 + 事后盘点纠正"，不强制留证。** 这是 2.9.3 在留证上的应用——**不是所有环节都值得付这个成本**（反方 13 的立场）。

#### 二、来源与取法

- **来源：既有视频监控系统，产品不自建。** 走国标（GB/T 28181）对接，只取实时流与回放流。**产品不生产影像，只做关联与调取。**
- **取法：不新增独立环节。** 沿用 7.8 的硬约束——影像与单据的关联由**事件锚点**自动完成，不由人工单独触发。

> **红队（对立方案）**：客户若没有既有监控系统，产品干脆配套一套轻量录像方案，卖点更完整。**否掉。** 录像是硬件与运维生意（摄像机、存储、供电、网络、现场维保），软件公司做它既无成本优势，又要承担 7×24 可用性责任——**与 §1.4 同一条逻辑：做自己不擅长的事，会拖垮擅长的事。**

#### 三、事件锚点是唯一的关联机制

作业动作**本身已经是系统事件**——扫码、称重、打印面单，全部自带精确时间戳、设备标识、操作人。影像片段以事件时间戳为锚，向前后各取一个窗口定位。

**7.9.1｜关联的粒度是「事件」，不是「画面内容」。** 系统能证明的是"某个动作在某个时刻发生、且有对应画面"，**不能证明"画面里的动作是什么"**。后者不是本文承诺的能力。

#### 四、证据的分层与固化

| 层 | 内容 | 留存 | 关键要求 |
|---|---|---|---|
| **全量层** | 视频系统的连续录像 | **3 个月**（Martin 2026-09-18 定），按录像机侧策略滚动覆盖 | **产品不承诺其可用性**，只在留存期内可调 |
| **固化层** | 关键节点的影像片段 + 关联单据 + 事件时间轴 | **长留存，年限覆盖争议窗口** | **不可改、不可单独删除**；完整性必须外部锚定 |

**7.9.2｜固化层的完整性必须外部锚定。** 本机自算的校验值存在自己库里没有意义——**改库即失效**。必须送**可信时间戳或第三方存证**。这是"对外举证"这一定性推出的直接产品义务。

**7.9.3｜全量层与固化层必须分离存储。** 混为一谈等于把举证能力交给录像机的存储策略，**而录像机的留存期不由我们控制**（国标接口只能取流，干预不了平台侧的录像策略）。**3 个月到期即不可回溯，这条必须写进合同。**

#### 五、画面可见性（本文新增维度）

**2.4.1 / 2.4.2 覆盖不到物理连续画面**，理由见新增的 2.4.4。

**7.9.4｜影像的隔离对象是「调取权限」，不是「画面采集」。**

- **采集面不隔离**：物理连续空间无法按货主切分；且**未经裁剪的完整性正是证据可采信的前提**——画面越"干净"，越像被选择性记录。
- **调取面必须隔离**：A 货主只能调取与自身作业相关的片段；**每次调取必须留痕**（谁、何时、哪一段、用途）。
- **共享作业区**（月台、拣货巷道、集货区、共用打包线）会被摄取，**这是物理事实，只能靠合同约定**——约定共享区会被拍摄、仅可调取与自身作业相关片段；**产品只做调取授权与留痕**（归 U23）。

**7.9.5｜影像不得直接对消费者可见。** 依据 §9.2「仓对消费者是盲的」。影像的用途收在**仓向货主自证**，以及货主向平台申诉时的转交。

#### 六、强制范围可配置

**7.9.6｜影像留证的适用范围按「货主 × 仓 × 货品类目 × 渠道」可配，默认档为关闭。**

依据约束 9（精度有成本）+ 2.10.6（平台合规要求是独立规则来源）。**默认全开等于给所有作业加动作，而大部分货主不需要**；只有挂上平台合规要求的组合才默认开启。**这与 7.8"不得对低值可补物料强制全量留证"是同一套逻辑。**

#### 七、本文明确不做的

1. **不承诺验证箱内装的是什么**——封箱后不可见。**写进需求等于在合同里承诺一个做不到的能力。**
2. **不把画面内容的自动解读作为证据陈述**——自动解读是**推断**，可被反驳；证据记录**不可**被反驳。二者的关系见 04 号专题。
3. **不对影像的可用性作承诺**——影像与留存期均由客户的监控系统掌握，产品只提供关联与调取入口。**影像取不到时生成"待补记录"并留痕，由仓线下取证**（见反方 22）。
4. **不新增独立留证环节**（7.8 硬约束）。

### 7.10 单据处理规则（v12 新增）

**这条规则管什么**：一张出库预报单在什么条件下被拆成几张出库单，以及拆不动时走哪条路。**它不是死规则，是可配对象**——阈值会随渠道、承运商、平台规则变，配在数据里比写在代码里对。

**两把刀，顺序不可颠倒**：

| 顺序 | 判据 | 性质 | 作用域 |
|---|---|---|---|
| **第一刀** | **不可混装**（品类互斥，如化学制剂与保健食品） | **硬约束**，命中必拆 | **全局**，不允许货主例外 |
| **第二刀** | **金额 / 体积 / 重量** 超阈值 | **可配**，阈值随渠道变 | **仓级**（阈值来自渠道约束） |

> **顺序为什么不能颠倒**：混装是合规红线，不能因为"金额没超"就不拆。

**混装约束的三条口径**（Martin 2026-09-26 裁定）：

1. **作用层级 ＝ 同一箱内不得共存**。
2. **全局约束，不允许「货主 × 仓」例外**——**并且不参与 02-2 §4.2.7 式的继承与例外机制**（该文档已同步声明）。不写这句，将来一定会有人照着模板给它做货主例外。
3. **来源分两档**：**法规型**（不可关闭，只能选拦或告警）／**商务型**（可关闭、可为个别货主调整）。**法规型的具体条目来源待补**（认定人 Martin、认定日期 2026-09-26，**来源后补**，见 U27）。

> **本文不做的（边界写死）**：**不校验"同车 / 同航班"级的运输隔离**——混装约束只到**箱级**。不写这句，它会以"系统怎么不管同车"的形式被反复问。

**执行与兜底**：

- 规则**由系统执行**，执行点在**出库预报单校验放行时**。
- **执行不了的一律进异常台账**（属"单据处理异常"，见 §7.3）——没有"为了让单走下去而放过"这条路。
- **允许云仓端人工改单**，但必须带**权限与留痕**，且**不得突破第一刀**（硬约束）。（Martin 2026-09-26 裁定）

## 八、度量

| 指标 | 口径要点 | 易被做假的地方 |
|---|---|---|
| 库存准确率 | 必须有明确分母：按库位数还是按货品数还是按金额；盘点覆盖率必须同时披露 | 只报差异笔数不报分母；用大额货品拉高准确率 |
| 时效达成率 | 起止时点必须写死（到货时点算卸货开始还是预报时间） | 起算点往后挪 |
| 单位操作成本 | 分母口径（单/件/行）必须固定；人工成本口径（含加班、含临时工）必须固定 | 换分母口径 |
| 容量利用率（v2 新增） | 必须先定义"满"是什么：按体积、按托盘位、还是按承重 | 用底面积算，层高不同的仓看起来一样满 |
| 货主留存 | 月度流失与流失原因归类 | 把流失算成"结算完成" |

> **度量本身是产品的一部分。** 指标口径不确定，度量就会变成营销材料。

## 九、上下游边界

### 9.1 接什么

| 方向 | 对接对象 |
|---|---|
| 上游订单 | 电商平台、货主 ERP、货主自有系统、表格导入、人工录入 |
| 下游履约 | 快递面单、承运商系统、物流轨迹 |
| **平台合规规则**（v10 新增） | **平台下发的标签规范 / 包装规范 / 箱规 / 装箱单格式**。**只读、可配、带版本，不主动抓取**（2.10.6、反方 18）。**注意与"面单"区分：面单是物流单，平台标签是商品标** |
| **物流渠道**（v12 新增） | **仓级主数据，由云仓维护**：渠道编码 / 承运商 / 约束（限重 · 限体积 · 限金额）/ 揽收方式。**渠道的选择权在货主**——在出库预报单上给出。**面单来源两档**：云仓打印 / 货主提供 |
| **交付方式**（v12 新增） | **送指定快递站点 / 承运商上门揽件**——它是**出库预报单上的执行属性**，不是仓的自由裁量 |
| 仓内硬件 | 手持终端、电子秤、打印机；后续自动化设备（分拣机、输送线、自动导引车） |
| **视频监控系统**（v11 新增） | **既有系统，产品不自建。** 走国标（GB/T 28181）对接，只取实时流与回放流。**用途与边界见 §7.9** |
### 9.2 不接什么

| 不接 | 理由 |
|---|---|
| 货主的销售与营销 | 不属于仓的业务范围 |
| 终端消费者客服 | **仓对消费者是盲的**：仓只看到"包裹"这一层，看不到订单的商业价值，也无法判断消费者诉求 |
| 财务总账与开票系统 | 仓只产出结算数据，不做会计核算 |
| **运输调度与路由**（v12 拆三段） | ① **渠道主数据**（有哪些渠道、编码、限重限体积限金额、揽收方式）**由云仓维护，作用域＝仓级**；② **渠道的选择权在货主**——在出库预报单上给定，**仓不替货主选**；③ **执行**（分堆、集包、交接、送站点或等揽收）在仓。**路由规划仍属货主或平台职责**。原文「承运商选择属货主或平台职责」过于笼统，会把①读成越界 |
| **工厂内部仓储与生产管理** | **v5 新增**。原料仓 / 物料仓 / 工单齐套 / 工序在制品，是 ERP 与制造执行系统的地盘（§1.4）。硬做只能做出一个残缺的制造执行系统 |
| **发往平台仓之后的库存** | **v9 新增，待 Martin 确认（U20）**。货按备货单发出、交接到平台仓之后，**它的在售、调拨、退货由平台管**。**我的倾向是不接**——仓的作业到"出库交接"为止。**但有一条必须接：退回仓里的货（场景 9）** |
| **平台的合规规则源** | **v9 新增**。产品**不主动抓取、不同步平台规则**，只提供**规则的配置位与版本留痕**（2.10.6）。规则变化的输入永远靠人 |

> **"仓对消费者是盲的"这条有直接产品后果**：系统不能按"销售额"给订单排优先级，只能按货主给定的优先级。仓没有判断商业价值的信息基础。

## 十、反方审查

> 本节按项目规则强制。以下 **23** 条是对本蓝图最强的反对意见，逐条回应。（原文写「20 条」时实为 22 条，v12 一并改正。）

### 反方 1｜这份蓝图默认"仓只做代管"，但三方仓普遍是自营 + 代管混合

一旦仓自己也卖货，约束 1（货权分离）和约束 4（数据隔离）全部漏掉一个位置——**仓自己是第 0 号货主**。自营货和货主的货在同仓争库位、争人力、争作业优先级。蓝图里没有这个位置，模型就会把它当例外打补丁。

**回应：本条已由 Martin 裁定关闭（2026-09-12，U2）。** 原话：「肯定是不自营的，不会有这样的业态。」

**先交代我在这条上错过两次：** v2 我拿"原料仓、物料仓是工厂自采"当依据 → v5 随工厂仓储移出而失效；v5 我又用"3PL 自有商品入仓很常见"当依据 → 现在被裁定否掉。**两次都是我把行业猜测当成了事实。**

**但这道异议的有效部分不能一起扔掉**：仓即便不自营，**仍会在特定时点持有货权**（留置 / 弃件 / 赔付取得 / 代垫）。原异议说"约束 1 与约束 4 漏掉了一个位置"——**在被动取得的情形下，这个判断依然成立。** 已用 §3.5 兜住，并留了反方 14 专门盯这条裁定的误读风险。

### 反方 2｜约束 1 和约束 9 的推论直接打架，裁决规则可能是假的

2.1.2 要求不可篡改流水，2.6.1 要求批次必填，都是**增加动作**；而 2.9.1 要求精度可调。同一个客户既要求"账必须准"又要求"别加动作"。我给的裁决规则是"按不可逆程度分档"——但**什么叫不可逆，是仓自己判断的，还是系统替他判断的？**

**回应：部分接受，裁决规则需补一层。** 分档必须**由系统给出默认档，允许仓调整但需留痕**。纯粹交给仓判断，结果是全仓降到最低档（省钱优先），约束 1 就废了。默认档 + 可调 + 留痕，是三者的唯一平衡点。

### 反方 3｜"来源无关"在 2.5.2 被我自己打了折，等于没有给出裁决标准

我写了"身份与状态机来源无关，作业语义来源相关"。但**哪些属性算身份、哪些算作业语义**，蓝图没给判据。没有判据，开发遇到新来源时会随手把语义塞进身份层，来源无关就烂掉了。

**回应：接受。** 需要给判据：**凡影响"库存怎么变"的，属身份层，必须归一；凡影响"包裹怎么打"的，属作业语义层，允许分化。**

### 反方 4｜度量一节没有回答"什么算失败"

整份蓝图只描述了"是什么"，没描述"什么是错的"。一份不含失败模式与红线的蓝图，指导不了后面的验收——验收时会变成"功能都做了就算完成"。

**回应：接受，但仍未补。** 需要一节「失败模式与红线」。它的判断依赖 U2 的答案，暂时列为待补项。

### 反方 5｜这套"约束 → 推论"的语言，在真实销售场景里没有说服力

仓主关心的是"能不能少雇两个人"，不是"货权与保管权分离"。一份不谈人效与成本模型的蓝图，在客户面前推不动。

**回应：部分接受。** 目标 C（单位操作成本）承担了一部分，但不够。缺的是**人效模型**——把每个作业动作折算成工时。**但这条是否要进产品设计，我不确定**：人效模型更像销售工具而非产品内核。列入 U9。

### 反方 6｜成本铁律可能过度压制功能设计

"任何增加作业动作的功能必须有收益对冲"——严格执行这条，会否掉所有"防呆"设计，而防呆恰恰是仓储系统价值最大的部分之一。

**回应：这条铁律不成立，已修正。** 2.9.3 给出了更好的口径：**按差错后果不可逆程度分档**，而不是按"动作数量"一刀切。成本铁律降级为**设计时的默认质疑**，不是硬性禁令。

### 反方 7（v2 新增，v5 关闭）｜"多仓"这条答案会把产品撑成通用仓储平台

U1 的答案不是"多仓"，而是"**多仓 + 多类型仓 + 三维空间**"。其中**工厂仓、原料仓、物料仓本质上是工厂内部仓储**，业务逻辑是"管自己的料"，而不是"替别人保管"。把它们纳入，产品定位就从"三方云仓软件"滑向"通用仓储平台"。

**后果**：内核要同时兼容两套业务驱动方式——**订单驱动（电商仓）与工单驱动（原料仓）**；单据类型翻倍；作业规则维度从"货品"变成「仓 × 货品」；还要额外处理工厂仓与电商仓之间的补货流转。**复杂度的增长不是线性的。**

**回应：本节的问题在 v5 已被定位裁定关闭——工厂仓储整体移出产品范围（§1.4）。**

不过过程值得记下来，因为**我在这里连续给了两次错答案**：

- **v2 的答案（错）**：按"驱动方式"分线（订单驱动 vs 工单驱动）。判据被证伪——电商仓内部也有组套。
- **v3 的答案（方向对，但问题问错了）**：说分界是"作业类型"，结论要"内核统一 + 差异做开关"。方向对，可**我把"工厂仓储要不要做"当成了一道产品设计题**——它根本不是产品题，是**定位题**。
- **v5 的答案（Martin 给的）**：不做工厂。**定位先定，边界自己就出来了**，根本不需要绕"内核统一还是分线"这一圈。

**留下的教训：我用模型设计技巧去化解一个定位问题，绕了两轮才回到原地。定位问题只能由定位解决。**

**当时的红队（v3 时我反对自己）**：把"物料消耗与产出"做成内核能力，意味着**每一个仓、每一个货主都要背着这套模型的复杂度**，哪怕他从不用组套——与约束 9（精度有成本）直接冲突。

**结论（仍有效，但适用范围被削小了一半）**：**模型层面必须全，界面与流程必须收**（按「仓 × 货品」开关，未启用则看不到操作）。已写进 7.7。

> 这一条现在只适用于**云仓内的组套 / 塑封 / 随附**。工厂侧的生产领用已不在范围内（§1.4）——**定位裁定顺手把这个红队问题也削掉了一半。**

### 反方 8（v2 新增）｜三维库位会把上架策略推成一个三维装箱问题，复杂度失控

2.8.2 把库位定义成"底面积 × 净高 × 承重"的三维容器，后果是**上架建议从"找一个空位"变成"三维装箱 + 承重分配 + 楼层约束"的优化问题**，复杂度不可控。

**回应：接受，但需要限定。** 本文的要求不是求解最优装箱，而是**能做可行性判断**（这批货放得下吗？超重吗？）加**简单规则排序**（同货品集中、重货低层、周转快的靠近出货口）。**最优解不是本蓝图的要求。** 这条必须在 02 里明确写成"约束校验 + 启发式排序"，而不是"优化求解"。

### 反方 9（v3 新增）｜组套会把产品拖成生产管理系统

2.10.1 要物料清单、2.10.2 要消耗产出记账、2.10.4 要预留组件——顺着这条线往下走，下一步必然是工单、工序、工时、在制品、排产。**仓储软件和制造执行系统之间的那条线，一旦开始模糊就收不住。**

**回应：接受，已用 2.10.5 划红线。** 但必须承认一点：**红线不能靠"我们不做"来守，得靠"做不了"来守**——即数据模型里**干脆不提供**工序、工时、在制品这些字段。**缺字段比缺功能有效得多。** 这条要写进 02。

### 反方 10（v3 新增）｜客供物料的入库源头完全不可控，这条流程可能根本不成立

货主"随手邮寄"包材和返利卡，意味着：无采购单、无条码、无预报、数量少、频率高，有时连发货通知都没有。**仓要先建档才能入库，而建档需要信息，信息又不在仓手里。** 更糟的是货主事后会拿"我寄了 500 张"来对账，而仓手上只有一个快递箱。

**回应：接受，而且我把这道题重写一遍——Martin 说看不懂，看不懂是出题人的错。**

**用最直白的话说：**

货主往仓里寄一箱返利卡，附了一句"寄了 500 张"。仓拆箱数出来 **480 张**。没有采购单、没有装箱单、没有条码。**系统能记录的只有"仓数出来 480"，系统没有任何办法验证货主寄了多少。**

那么这 20 张的差额，**谁认账？**

- 仓认 → 仓凭白赔 20 张，而且会被反复薅。
- 货主认 → 货主说"我明明寄了 500"，凭什么信你数错了。
- 双方都不认 → 每次入库都吵一架。

**我的判断（推论）：这是产品解决不了的问题。** 产品只能做两件事——把"实收 480"**当场、及时地**回传货主确认；把差额挂成异常台账，可追溯、可结案。

**但"以谁的数字为准"必须写进合同。** 行业里的常规写法是"以仓入库实收为准，货主随寄须附装箱单；无装箱单的，以实收为终"。

**所以要你拍的只有一句话：认不认这个办法（合同定数字口径 + 产品只管回传与留痕）。**

**裁定（Martin，2026-09-12）：「认这个办法。」U14 关闭。**

裁定之后，产品的义务边界随之固定为三件：**入库存证 → 当场回传货主确认 → 差额进异常台账并可结案**。产品**不承担**"验证货主寄了多少"的责任，因为它拿不到这个信息。

**但裁定之后必须补一条推论，否则这个口径是空的：**

**"以实收为终"能站得住的前提，是实收数可被货主验证。** 一份没有影像、没有重量、没有封条记录的"480 张"，在纠纷里就是仓自说自话——**合同条款会因为缺证据而落空**。所以**入库留证从"最好是"变成"必须有"**，与合同口径捆绑，见 §7.8。

### 反方 11（v4 新增）｜剥离分期之后，蓝图会变成一份"读起来对、落不了地"的东西

不分期的蓝图，读者分不清哪个是"必须有"、哪个是"最好有"，下游失去抓手，最后还是要回来问"到底先做什么"。

**回应：部分接受，但不改。** 分期不是蓝图的抓手，是 `03-产品化切分表` 的抓手。蓝图区分"必须"与"可选"的办法不是分期，而是**推论与目标的挂接**（§2.3）——挂在目标上的是必须，挂不上的不该存在。**把两份文档的职责压进一份，才是真正让下游失去抓手的原因。** 接受的部分是：03 必须尽快产出，否则"先做什么"确实无处可查。

**红队**：折中方案是蓝图里只给"依赖顺序"、不给"期"。**这个折中我否掉**——依赖顺序同样是 03 的内容，蓝图里再放一层就是重复，两处都要维护，必然不一致。

**未决项的诚实交代**：原 U3、U4、U8 三条，我在 v4 里用推论把它们"定"了（四个位置必须能表达 / 费用账必须对货主可见 / 货主可见面必须存在）。**这是我用推论替你下的判断，不是你的确认。** 依据都写在 11.2 表里，**你若不认某一条，直接说，我改回未决。**

### 反方 12（v5 新增）｜"专心搞云仓"会丢掉工贸一体客户，而这类客户往往单子最大

工厂自己既做生产又做电商仓储的客户，要的是一套系统管全部。我们不做工厂侧，他们就得买两套、还要跨系统对补货。**这类客户的单子通常比纯三方仓大。**

**回应：接受这个损失，且我认为这个取舍是对的。** 上一版我给的三条论证全错（见反方 7 的复盘）。真正的理由是：**工贸一体客户的核心诉求在生产侧，不在仓储侧。** 我们服务的是他的仓库，可他的痛点在产线。这种客户哪怕签下来，也会不断要求往生产侧长——**最后我们还是被迫去做制造执行系统，只是从"主动选择"变成了"被牵着走"。**

**红队（对立做法）**：不追求内核统一，把工厂侧做成一个**可选独立模块**——纯云仓客户不装，工贸一体客户加装。**条件**：客户群里工贸一体占多数，且他们真正要的是"一套系统"而不是"功能全"。**回应：我否掉。** 这等于在一个产品里维护两套业务逻辑，而两套逻辑会在**库存、单据、库位、权限**这四层反复打架——**"可选模块"只是把耦合藏起来，不是消除它。**

### 反方 13（v6 新增）｜"以实收为终"会拆掉仓"数得准"的经济激励，而留证又要仓加动作——两头都指向约束 9

这条裁定有个自相矛盾的地方，我必须挑明：

**第一面**：既然合同认"以实收为终"，那么**差额不归仓负责**。仓数出 480 就是 480，货主说 500 也没用。**结果是仓失去了把这一箱数清楚的经济动机**——多花十分钟数仔细，收益是零，成本是十分钟人工。理性选择就是"快速数一遍，报个数，结束"。

**第二面**：而为了让这个口径可被信任，我们又要求仓**留证**（拍照、称重、记封条）。**留证是加动作，直接撞约束 9（精度是有成本的）**——系统每加一次确认动作，都变成仓的人工成本。

**两面合起来就是**：一边免除仓的责任，一边要求仓为免责而付出成本。**仓的天然反应是"证据随便拍拍，数还是随便数数"。这个口径有被架空的实际风险。**

**回应：接受，靠两件事限定，不靠呼吁。**

1. **留证强度必须分档，与 7.5 同一套判据**——按**差错后果的不可逆程度 + 货值**。返利卡、包材这类低值可补物料，留证到"拍照 + 数量"即可；高值或不可补的客供物料，才上称重与封条。**不搞一刀切全程录像。**
2. **留证动作必须设计成"顺手做"，不是新增一道工序**——挂在既有的入库扫码动作上（扫一下 = 完成计数、拍一张 = 完成留证），**不允许多出一个"留证"环节**。这就是 2.9.3 的应用：**降低精度的成本，而不是降低精度。**

**之所以不能靠呼吁解决**：仓不会因为"要讲诚信"就去多花十分钟。**制度设计只能让正确动作的边际成本接近于零。**

### 反方 14（v7 新增）｜"不会有这样的业态"这句话，最危险的后果是被下一代实现者读成"模型里禁止仓出现在货主位置"

**先把这句话的两种读法分开，因为它们对错相反：**

- **读法一**："我面向的客户群里，没有既做自营又做代管的云仓。" → **这是市场定位，成立，我不反对。**
- **读法二**："仓储与自营在物理上不可能共存。" → **这是行业事实断言，我反对。** 现实里存在：平台自建物流既接三方业务也做自营；云仓用自营爆款填闲置产能；工厂转做云仓后自家尾货还压在仓里。**这类形态存在，只是不是我们的目标客户。**（这一点我判断不了对错——Martin 是行业里的人，他有我没有的信息；我用它作为**红队提醒**，不作为结论。）

**但真正要命的是第三件事，与上面两种读法都无关：**

**"被动取得货权"躲不掉**（留置 / 弃件 / 赔付 / 代垫，见 §3.5）。它跟自营没有一分钱关系。

**如果实现者把"不自营"落成一条硬约束——"仓的运营方不得出现在货主位置"——那么这四类场景在系统里全部无处安放**：留置的货挂不到任何人名下、弃件的货无法变更归属、赔付取得的残值无处可记。它们只能走线下台账，而线下台账与系统库存必然对不上。

**回应：接受这个提醒，已用 §3.5 划清界限。** 措辞上我做了刻意的区分——**不建"自营经营"能力 ≠ 禁止"所有权变更"**。

**红队（对立做法）**：为了模型纯粹，彻底禁止仓出现在货主位置，碰到留置 / 弃件就走**"报损出库"**抹平。**否掉。** 报损出库会**伪造责任归属**：明明是所有权转移，记成货损——**货主的准确率统计里会背上不属于他的差异**。这同时破坏约束 1（变动流水必须真实）和约束 3（货主是客户）。**用假账解决模型洁癖，代价是把最重要的信任给卖了。**

### 反方 15（v8 新增）｜"可售商品也能被组合"，把一个技术问题变成了商务问题，而且它推翻的不只是分类

**先认账**：这条是 Martin 指出的。v3 的"可售商品 / 物料"二分法**是我把用途当成了货品的固有属性**，错因写在 2.1.5。

**但它牵出的真麻烦不是分类，是库存争用：**

当组件是**可售商品**时（A、B 组成套装 C），系统必须回答一个**没有纯技术解**的问题：

**这 100 个 A，是留着单独卖给下单的消费者，还是拿去做套装 C？**

- v3 时期"组件"默认是物料（包材、返利卡）——那批东西本来就不能卖，占不占用无所谓。**现在占用的是能卖钱的货。**
- 2.10.4 原本写"组装必须预留组件"。**这句话在组件是可售商品时，等于授权系统把货从订单手里抢走。** 对外承诺时限（约束 3）与组装需求之间的冲突，第一次成了真冲突。

**这是商务判断，不是技术判断**：A 单独卖的毛利和组装后卖的毛利，哪个高？A 缺货时，先保订单还是先保组装线？

**回应：接受，已开 U17 交还给 Martin。** 我不替他定——决定它的是货主合同与仓的经营策略，不是模型。

**红队（对立做法）**：干脆禁止"可售商品当组件"，只允许物料进物料清单。**否掉**——Martin 已指出可售商品会被组合，这是真实业态；禁止它等于把最常见的组套场景（组合优惠、买 A 送 B）挡在门外。

**还有一件必须承认的事**：**我上一轮宣布"§11.1 业态事实已清空"，它撑了不到一轮。** 原因是我把 01 的完备性估计得过高，**而这个判断本不该由我宣布。** 已改回 1 条。这件事顺手证明了一件事：**文档的完备性只有被攻击过才成立，自己宣布没有意义。**

### 反方 16（v9 新增）｜"标识层"是我把一个包装动作过度升级成了数据模型问题

**站在一个做了十年仓管主管的立场上说**：贴标哪有那么玄。我们仓里贴的标，一大半是印好的固定内容——产地标、成分标、警示标、69 码。**印什么、贴哪儿都是固定的，贴完就完了，不需要什么"标识集合"。** 你说要建一层编码映射，那是给平台代发的大电商仓才需要的东西，**对大多数客户就是多加一张配置表。**

**回应：部分接受，并且接受它决定这件事是"配置"还是"内核"。**

要区分的是两类东西：**固定内容标**（内容不变、无映射，贴错也不过是重贴一张）和**平台分配的动态 SKU 码**（内容由外部给、必须与单据匹配，错了整批拒收）。前者确实只是耗材加工。

**但设计上必须容纳后者**——因为后者恰恰是这类云仓的主要业务来源（平台备货是现金流）。**所以它不能"不做"，只能"按开关决定启不启用"。** 这条限定我接受，已写进 2.1.8。

### 反方 17（v9 新增）｜"加工态是可变属性"会让系统说"有 500 件"，实际只能发 300 件

**这是本轮最怕的一条，站得住。**

如果把"套袋贴标后的货"和"裸货"当成**同一个货品**的两种属性，就会出现：系统里查到有 500 件，其中 300 件已套袋贴 TEMU 标、200 件是裸货。来了一张 TEMU 单要 400 件，**系统报"库存充足"，实际只能发 300 件。**

**这是不可逆错误**（撞 2.9.3：错发货品、发错货主 → 强制校验）。而且最恶劣的地方是**发现得太晚**——不是在拣货时发现，是货到了平台仓被拒收时才暴露。

**回应：反驳不了，接受。** 必须补一条硬约束：**加工态可变，但可用量必须分状态统计。** 可用量不是"货品有多少"，是"**货品 × 加工态**有多少"。**这条直接否掉"属性可变就等于不用管"的偷懒读法。**

**但它没有否掉"不拆 SKU"的方案**——它只是说：**不拆 SKU 就必须额外做可用量分状态统计；拆 SKU 不需要，代价则转移到货主建档上。两条路的代价都真实存在，这正是 U18 要拍的原因。**

### 反方 18（v9 新增）｜"平台规则可配置"很可能是一张空头支票

**站在一个正在考虑换系统的仓负责人立场上**：平台一年改好几次标签规范、箱规、发货要求。你让我在系统里配——**谁配？多久配一次？平台昨天发的通知，我今天就得改？** 配错一次，一整批发出去被拒收。**我宁愿打电话问货主。**

**回应：接受，并把承诺缩小到能兑现的范围。**

产品能兑现的是：**规则可配、带版本、变更留痕、历史单据仍可解释**（"这单是按当时哪一版规则做的，能查"）。
产品兑现不了的是：**自动跟平台规则同步。**

**把做不到的写进承诺就是空头支票。** 已把这条边界写死在 2.10.6。

### 反方 19（v9 新增，v10 重写）｜套袋贴标的位置——我上一轮猜错了

**上一轮我写的是"套袋贴标可能是入库流程的节点"，还配了一个模拟的云仓运营者立场来支撑它。Martin 直接否掉：这是出库流程中的动作。**

**我错在哪，交代清楚：** 我拿"很多云仓货一进来就贴标"这条**行业印象**当成了业态事实去推。**这是同一类错误的第三次**——v2 拿"原料仓是工厂自采"，v5 拿"3PL 自有商品入仓很常见"，v9 拿"入库即贴标"。**三次都是把行业猜测当事实**，而这正是项目规则明令禁止的行为。

**更值得记的一条方法教训：红队机制不能替代业态事实。** 我让"一个模拟的云仓运营者"开口反对，读起来很有说服力，但**那个角色也是我编的**。它编错的时候比没有红队更危险——**因为它给错误观点披上了"对立面已受检验"的外衣。红队的价值是逼出对立面，不是生产事实。**

**但它有一个有效部分留下来了，而且换位之后更有分量：**

| 加工发生在 | 触发 | 计费归属 |
|---|---|---|
| **出库流程的节点** | 随订单执行 | 算**出库操作费**，还是**独立增值服务费**？ |
| **库内增值作业** | 货主单独下指令 | **独立计费**（毛利来源，见 1.1） |

**同样的动作，放在不同位置，计费结论相反。** 现在问题变成"出库加工到底单不单独收费"——**这是商务判断，见 U21。**

### 反方 20（v10 新增）｜把加工放进出库关键路径，是用时效换通用性

**站在一个正在跟别家云仓比价的货主立场上**：我选仓首先看出货快不快。你告诉我"拣完还要套袋贴标再装箱"——**这一单要多花几分钟？大促的时候这道工序卡在哪个环节？** 别的仓提前把标贴好，拣出来就装箱，你的仓得在现场慢慢做。

**这条攻击是有效的，因为它撞的是目标 B（时效达成率）。**

**回应：接受这个代价，但要把它说成"取舍"，不是"缺点"。**

- **按单现场加工的代价**：占打包工位、拉长出库时长、大促时是瓶颈。**换来的是库存通用性**——同一件货可以发给任何平台。
- **预先加工的代价**：库存变成"定向库存"，**只能发一个平台**。平台单没来、规则改了、或量估错，这批货就砸在手里。**换来的是出库快。**

**所以答案不是二选一，而是"两个都要，但默认必须按单现场加工"**（2.10.7）——预先加工只能是货主明确要求、且愿意承担定向风险时的选项。

**红队（更狠的一条，我否掉了）**：**接到备货单就预先加工，把时效抢回来。** **否掉理由**——备货单本身常常是"先备货、后分派"，同一批备货可能分给不同平台（这正是 Martin 这条纠正的事实基础）；而且提前加工会让库存里躺着大量定向货，**平台侧一变动，损失直接落在货主头上，仓也要被追责。不能为了出库快而把风险转嫁给货主。**

### 反方 21（v11 新增）｜影像解决不了数量准确性，而数量争议恰恰是收货留证的唯一理由

**站在一个做了十年仓管主管的立场上**：你说要给收货留证。收货要证的是什么？是"我数出来 480 件"。影像能证明这个吗？**不能。** 镜头拍不到箱子里有几张卡；拍得到员工在数，数得对不对看不出来。

**这条反驳不了，接受。** 影像证明的是**过程存在与动作序列**（有人卸了货、有人扫了码、有人封了箱），**不是数量准确性**。数量准确性靠的是 7.8 的"当场回传货主确认"与"差额进异常台账"——**影像只是让"仓确实按流程做了"这件事变得可查。**

⇒ 已写进 7.9 第七节第 1 条。**把影像当成数量争议的解药，是错的用法。**

### 反方 22（v11 新增）｜产品承担了举证承诺，却没有举证能力 —— 本方案最大的结构性风险

**站在一个软件公司老板的立场上**：影像不在我手里（是客户的海康系统），留存期不在我手里（是客户录像机的策略），运维不在我手里。**但界面是我出的、关联规则是我定的。**

出事时货主不会去找监控厂商，他会说："你们系统里那个视频链接点不开"、"你们说有关联，可这段调不出来"。**我承诺了一个我没有能力兑现的东西。**

**回应：接受，这是本方案最大的结构性风险，且没有纯技术解。** 出路只有一条——**把边界在合同与界面上同时写死**：

1. 产品只做**关联与调取入口**，**不对影像的可用性、完整性、留存期作承诺**（7.9 第四节、第七节第 3 条）。
2. 影像不可用时**生成"待补记录"并留痕**，由仓线下取证——**把失败显性化，而不是假装成功**。
3. **全量层 3 个月到期即不可回溯**这件事，必须写进合同与界面提示，**不能让客户在争议发生那天才发现**。

**红队（对立方案）**：干脆不接视频，让客户自己去监控平台上调。**否掉**——那就没有事件锚点，调证靠人回忆时间点，等于没有留证能力。**接了有交付风险，不接就丢掉这个能力的全部价值；两害相权，接，但把风险显性化。**

### 反方 23（v12 新增）｜"拆单规则可配 + 系统执行 + 异常兜底"这条链，把三个未验证的假设串成了一条通路

**反对**：这条链看起来完整（可配规则 → 系统执行 → 执行不了进异常台账），但它同时依赖三个我没验证的假设——① **箱级混装约束要上卷到出库单**（否则"一次预报必拆两张出库单"不成立，U24）；② **规则引用的字段缺失时不算"执行不了"**（若算，几乎每一张信息不全的预报单都会掉进异常，U25）；③ **为作业异常设计的台账能装下单据处理异常**（U28）。

**回应：接受，这是本版最大的结构性风险。** 三条任一不成立，这条链就在中途断掉——**而断点不在设计阶段暴露，在运行期表现为"某些单永远拆不对、异常台账里挂着没人认领"**。

三处都已单列未决，并各自给出不成立时的替代路径：不上卷 → 混装只在装箱环节拦，出库单不拆；缺字段 → 进异常（则要接受异常量）；台账装不下 → 第二本台账。**但这些替代路径同样未经推演，本版只是把风险从暗处挪到明处。**

| 单证体系 | 出库起点＝**出库预报单**（货主端创建）· 入库起点＝**入库预报单**（原"到货预报"改称）· 预报单与出库单**是两张单**（引用关系，非一张单的两个状态） |
| 拆单 | 一张预报单**只指定一个仓**，可拆出 **N 张出库单**；判据＝**不可混装（硬约束）** + **金额/体积/重量阈值（可配）** |
| 混装 | 作用层级＝**同一箱内不得共存**；**全局约束，不允许货主例外，不参与继承与例外机制**；来源分法规型 / 商务型两档 |
| 选仓 | **由货主端决定，云仓不参与选仓建议**；选仓规则将来在货主端做 ⇒ **本项目不存在"寻源拆单"** |
| 执行 | 规则**由系统执行**；执行不了**进异常台账**；**异常台账必须分类**；**允许云仓端人工改单**（带权限与留痕） |
| 扣减与拦截 | 库存**实际扣减＝交接时**（拣货预占）；货主**可拦截窗口＝集包完成之前**，之后走**快递拦截 → 返库** |
| 渠道 | **物流渠道＝仓级主数据，由云仓维护**；**选择权在货主**（预报单）；面单可由货主提供；交付方式含**送指定站点 / 承运商上门揽件** |
| 增值能力 | 未启用则**货主端不可选**（双闸门：货主端候选集过滤 + 云仓端校验） |
